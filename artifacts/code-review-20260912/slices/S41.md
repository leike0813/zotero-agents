### F1 [P2][并发/正确性] src/modules/acp/chat/acpSessionManager.ts:3329 —— 删除会话未取消 persist 定时器，2s 内会把已删会话写回索引（复活）

- 证据：
```ts
  deleteAcpConversationState(backendId, deletedConversationId);
  sessionRuntimes.delete(sessionRuntime.key);
```
（定时器本体）
```ts
  sessionRuntime.persistTimer = setTimeout(() => {
    sessionRuntime.persistTimer = null;
    persistSessionRuntimeSnapshotNow(sessionRuntime);
  }, STREAMING_PERSIST_THROTTLE_MS);
```
- 分析：`persistSessionRuntimeSnapshotNow` 只要求 `snapshot.backendId && snapshot.conversationId` 非空（847-855），二者在删除后被删除仅从 `sessionRuntimes` map 移除，对象字段仍在。任何在删除前 2s 内触发过 `throttlePersist` 的 emit（chunk/usage_update/available_commands_update 等，1664-1757）都会留下 pending 定时器；定时器随后调用 `saveAcpConversationState` → `upsertPluginTaskRequestEntry` + `writeAcpChatSessionIndex`，把 `conversation:<backend>:<id>` 与索引摘要重新写回。结果是：会话在侧栏「复活」，但 transcript 目录已在 `deleteAcpConversationState` 中被删除，打开后为空——数据状态不一致。`archiveAcpConversation` 无此问题（索引项仍保留并保留 archivedAt）。
- 建议：删除/归档/切换前统一清理该 runtime 的 `persistTimer`/`workspaceChangeTimer`（或在 `persistSessionRuntimeSnapshotNow` 加「该 key 是否仍在 sessionRuntimes/该 conversationId 是否仍有效」的校验）。
- 置信度：中高

### F2 [P2][数据丢失] src/modules/acp/chat/acpSessionManager.ts:3805 —— 名为「prune runtime」的函数会清空被移除后端的全部会话持久化数据

- 证据：
```ts
  for (const [backendId, teardowns] of teardownByBackend) {
    void Promise.allSettled(teardowns).then(() => {
      clearAcpConversationState(backendId);
    });
  }
```
- 分析：`clearAcpConversationState`（acpConversationStore.ts:960-983）删除该后端所有 conversation request entry、session index entry，并对每个 session 调用 `removeConversationStorageDir` 删掉 transcript 目录。触发条件：调用方把某个已配置后端漏在 `backends` 入参里（注册表加载不全、被识别为 ACP 之外、临时不可用），即整后端历史被删除。函数名与文档只承诺「prune session runtimes」，行为却是破坏性数据清理，属于名称/行为不符 + 潜在数据丢失；调用方不在本切片，无法确证是否只在用户显式移除后端时调用。
- 建议：把「移除运行时」与「删除持久化数据」拆成两个入口，数据删除只由显式用户操作触发（或改为标记/归档而非物理删除）。
- 置信度：中（行为确证；触发路径需主代理核对调用方）

### F3 [P2][错误处理] src/modules/acp/chat/acpConversationStore.ts:484 —— 目录删除 fire-and-forget，失败被静默吞掉并产生 unhandled rejection

- 证据：
```ts
  const paths = resolveAcpChatRuntimePaths(backendId, conversationId);
  void removeRuntimePath(paths.conversationStorageDir);
```
- 分析：`void` 不接收 rejection。`removeRuntimePath` 若是 async（同文件 8 处调用、其余均 await 或 .catch），删除失败会变成未处理的 Promise rejection；同时调用方（`deleteAcpConversationState`/`clearAcpConversationState`）已在同一流程中删除了 store 记录，留下孤儿目录且无任何诊断，后续同 id 重建会话会读到旧 transcript 残留。
- 建议：改为 `await` 并把失败降级为 `appendDiagnostic`/返回错误，或在内部 `.catch()` 中记录。
- 置信度：中高

### F6 [P2][正确性] src/modules/acp/chat/acpChatTranscriptMirror.ts:486 —— `normalizeAcpChatTranscriptPageLimit` 对非数值入参返回 NaN

- 证据：
```ts
  return Math.max(
    1,
    Math.min(
      ACP_CHAT_TRANSCRIPT_PAGE_MAX_LIMIT,
      Math.floor(Number(value || ACP_CHAT_TRANSCRIPT_PAGE_DEFAULT_LIMIT)),
    ),
  );
```
- 分析：`Number("abc")` 为 NaN，`Math.floor(NaN)`/`Math.min(NaN)`/`Math.max(1, NaN)` 全为 NaN，钳制完全失效。调用点 `readAcpConversationTranscriptPage`（acpChatWorkspaceDataPlane.ts:565、592）与 `readAcpChatTranscriptMirrorPage`（514-517）会把 `args.limit` 原样传入，因此对外返回的 DTO `limit` 字段可能是 NaN，并原样下传给 page reader 参与游标/切片计算（截断窗口 → 空页或全量页，取决于下层实现）。注意 `value=0` 会被 `||` 折成默认 80，而非钳到 1。
- 建议：先 `Number.isFinite` 校验再钳制，非有限值回落到默认值。
- 置信度：高（NaN 产出可确证；下游影响程度 中）

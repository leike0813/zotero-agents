## B. Findings

### F1 [P1][并发] src/modules/synthesis/sidecar/synthesisSidecarRuntimeSupervisor.ts:452 —— stale generation 的 `fail` 直接 return，launch 在 `stop()` 之后仍会 spawn，导致 native sidecar 进程泄漏
- 证据：
```
    if (launchGeneration !== generation) {
      return;
    }
```
（对应 launch：`const install = options.resolvedInstall ?? (await installer.ensureInstalled());`（592-594）之后、`subprocess.call`（634）之前/之后都没有 generation 或 `controlledStop` 复检）
- 分析：`stop()`（707-709）执行 `generation += 1; controlledStop = true`。若此刻 launch 正卡在 `await installer.ensureInstalled()`（首次安装可达数秒），`session` 仍为 null，stop 不会 kill 任何东西；install 返回后 launch 继续 `session = current`（603）、写 config、真正 spawn 进程，随后 `waitForDiscovery` 因 `!controlledStop` 立即退出并抛 `sidecar_discovery_timeout`（504-519），catch 调 `fail(..., launchGeneration)`（703）→ generation 已变 → 直接 return，既不做 `stopProcess` 也不做 `cleanupSession`。结果：快照显示 stopped，但有一个 native 进程存活（持有 repository DB 锁/监听端口），session 目录残留；下一次 start 会再拉一个进程。任何 stale `fail` 都会走这条“只 return 不清理”的路径。
- 建议：launch 在每个 await 之后（install 后、spawn 后、handshake 后）复检 `launchGeneration !== generation || controlledStop`，命中则 `await stopProcess(current); await cleanupSession(current);`；或在 `fail` 的 stale 分支中当 `current.proc` 已存在时强制清理。
- 置信度：高

### F2 [P2][错误处理] src/modules/synthesis/sidecar/synthesisSidecarRuntimeInstaller.ts:288 —— 安装已成功但删除 oldRoot 失败会被整体判为 corrupt
- 证据：`await removeRuntimePath(oldRoot);`（位于 try 内，catch 为 `return diagnosticSnapshot("corrupt", target, \`install_failed:${errorCode(error)}\`)`）
- 分析：swap 完成且 `verifyInstalledRuntime` 已返回 ready（278-287）之后，才执行 oldRoot 清理；该调用会抛错（同文件 291 行与 supervisor 427 行都用 `.catch(() => false)` 兜底，说明可抛），Windows 上旧二进制被仍在运行的旧 sidecar 占用即触发。异常落到 catch → 返回 `corrupt`/`install_failed:*` → supervisor `validateInstall` 抛错 → 状态 unavailable + `manual-recovery-required`，尽管 currentDir 是可用安装。
- 建议：把 oldRoot 清理移出关键路径（`.catch(()=>false)` + 下次启动清理），或在 catch 中先复验 `paths.currentDir` 再决定返回 ready 还是 corrupt。
- 置信度：中

### F3 [P2][资源] src/modules/synthesis/sidecar/synthesisSidecarRuntimeInstaller.ts:246 —— `.old-<nonce>` 残留目录永不回收
- 证据：
```
    const nonce = `${Date.now().toString(36)}-${Math.random()
      .toString(16)
      .slice(2)}`;
```
（254-255 行只 `removeRuntimePath(stagingRoot) / removeRuntimePath(oldRoot)`，两者都带“本次”nonce）
- 分析：nonce 每次 `performEnsure` 重新生成，因此清理只能命中本次调用的路径。任意一次安装“已把 current 移走/已发布新 current，但在删除 oldRoot 前失败（含 F2 情形）或进程退出”，都会在 runtimeRoot 下留下 `current.old-<旧nonce>`（完整 bundle，数十 MB），后续调用永远不会碰到它 → 磁盘无界累积。
- 建议：安装开始时按前缀扫描清理 `*.old-*` 与 `*.staging-*`，或改用固定名 `current.old/current.staging` 并在 ensure 入口清理。
- 置信度：中

### F4 [P2][并发] src/modules/synthesis/sidecar/synthesisSidecarRuntimeSupervisor.ts:548 —— 健康检查 await 后不复验 session 归属，可发布陈旧健康并以非当前 session 触发重启
- 证据：
```
        const health = await controlClient.health(current.connection);
        publish({
          ...narrowSynthesisSidecarHealth(health),
```
- 分析：`current` 在 await 之前捕获（定时器路径 544/548，`observeHealth` 784/793）。await 期间若发生重启（旧进程退出 → fail → 重 launch 建立新 session），返回后仍把旧实例的 serviceInstanceId/bundleId/computePool 写进快照（覆盖新实例）；若 `computePool.state === "degraded"` 或 health 抛错，则调用 `fail("sidecar_compute_pool_degraded"/"sidecar_health_failed", current)`，默认 `launchGeneration = generation` 已是新一代 → 通过 452 行的 stale 守卫 → `clearTimers()` 清掉新 session 的 health 定时器，`session === current` 为假所以不清 session，却照常发布 unavailable 并安排重启 → launch 覆盖 `session`，新进程被孤立（与 F1 同源泄漏）。
- 建议：await 之后先判 `session === current && !controlledStop`，不成立即 return（不 publish、不 fail）；`fail` 入口加 `if (current && session !== current) return;`。
- 置信度：中

### F6 [P3][性能] src/modules/synthesis/sidecar/synthesisSidecarRpcClient.ts:239 —— 同一请求串在每次调用中被 `TextEncoder.encode` 三次
- 证据：
```
        textEncoder.encode(requestSource).byteLength >
        (isCompute
          ? SYNTHESIS_SIDECAR_LIMITS.computeRequestBodyBytes
          : SYNTHESIS_SIDECAR_LIMITS.requestBodyBytes)
```
（253 与 265 行又各 encode 一次同一 `requestSource`）
- 分析：compute 请求上限可达 MB 级，`JSON.stringify` 之后再做 3 次全量 UTF-8 编码（含成功路径的 metrics），属热路径上的重复分配；上限校验与埋点复用同一值即可。
- 建议：`const requestBytes = textEncoder.encode(requestSource).byteLength;` 计算一次并复用。
- 置信度：高（判断，非缺陷）

### F7 [P3][资源] src/modules/synthesis/sidecar/synthesisSidecarTrace.ts:119 —— `active` 的 trace 永不驱逐，1000 事件上限不是硬上界
- 证据：
```
    const candidate = [...traces.values()]
      .filter((trace) => !trace.active)
      .sort((left, right) => left.updatedAtMs - right.updatedAtMs)[0];
    if (!candidate) return;
```
- 分析：`trace.active = trace.rootActive || activeMaintenanceOperationIds.size > 0`（203-204），而 `rootActive` 只在收到 `parentSpanId === undefined && outcome !== "started"` 的 root 终态事件时置 false（161-162、202）。若某条 trace 的 root 终态从未被观测到（例如 native 进程在终态事件前退出、或带 parent 的 span 永远收不到 root 终态），它会永久 active 且不被逐出 —— `traces` 映射与 `maintenanceOperationOrigins`（不受事件上限约束）可无界增长，每条最多再占 128 个事件。
- 建议：对 active trace 增加时间上限（超过 N 分钟强制标为 inactive 或裁剪事件），并让总量上限在无候选可逐出时至少裁剪最旧 trace 的事件。
- 置信度：中

### F10 [P3][契约] src/modules/synthesis/sidecar/synthesisSidecarComputeClient.ts:31 —— 每能力 deadline 常量导出后未接线，layout 实际使用 5s 默认
- 证据：
```
export const SYNTHESIS_SIDECAR_COMPUTE_DEADLINE_MS = 5_000;
export const SYNTHESIS_SIDECAR_LAYOUT_DEADLINE_MS = 10_000;
export const SYNTHESIS_SIDECAR_METRICS_DEADLINE_MS = 5_000;
```
（构造只使用 `deadlineMs: options?.deadlineMs ?? SYNTHESIS_SIDECAR_COMPUTE_DEADLINE_MS`，`computeCitationGraphLayout` 不传能力级 deadline）
- 分析：接口上 layout 被声明为 10s、metrics 5s，但客户端默认给三个能力统一 5s；若调用方（本切片外）依赖这三个常量而非显式传 `deadlineMs`，layout 会在 5s 被 `worker_timeout` 截断，且 `SYNTHESIS_SIDECAR_LAYOUT_DEADLINE_MS/METRICS_DEADLINE_MS` 成为死导出。需与 `defaultClient`/workbench 适配层核对调用点后才能定性。
- 建议：把能力级默认放到 compute 分派处（layout→LAYOUT，metrics→METRICS），或删除未接线的常量。
- 置信度：中（判断）

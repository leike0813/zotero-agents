## B. Findings

### F1 [P2][性能] src/modules/skillRunner/run/skillRunnerTaskReconciler.ts:369-374 —— 台账校准对“全部历史 requestId（含已归档）”串行双查后端，无终态/归档短路
- 证据：
```
    for (const requestId of requestIds) {
      try {
        const terminalRunState = await resolveDoubleConfirmedTerminalRunState({
          client,
          requestId,
        });
```
- 分析：`requestIds` 由 `collectRequestIdsForBackend` 汇总 active tasks + dashboard history + **全部 run records**（:212-240），未过滤 `archivedAt` 或已终态记录；每次迭代至少 1 次、确认终态时 2 次 `getRunState`（:190-202），全部串行 await。触发条件：startup 校准或任一 backend 由不可达转可达（`handleBackendHealthChange` → `spawnBackendRecoverySweep`）。影响：用户在界面上 purge 掉的 run 会转成 archived 记录长期留存，每次 sweep 都重新发 2 次 HTTP，历史越长成本线性增长且阻塞本轮其它 run 的恢复。
- 建议：收集阶段排除 `archivedAt` 非空记录；对可用 store 状态判定“台账已终态且与后端一致”的 requestId 直接跳过，并给剩余项加并发上限。
- 置信度：中

### F2 [P2][性能] src/modules/skillRunner/run/skillRunnerRunStore.ts:1415-1428 —— requestId 直查未命中时全表加载并逐条 `JSON.parse`，成本被诊断计数掩盖
- 证据：
```

  const candidates = listPluginRunStoreEntriesFiltered("skillrunner", {})
```

- 分析：`listPluginRunStoreEntriesFiltered("skillrunner", {})` 拉取该 kind 的**所有**持久化 payload，`parseRecord` 内部对每条执行 `JSON.parse`（:625-627），随后排序取最新（:1424）。该方法被前台续跑/协调器按 requestId 高频调用，任何一次直查索引未命中都会重复付出 O(N) 解析；而计数只在 :1426 加 1 次 `fullPayloadReadCount`，使读放大在诊断里不可见。

### F9 [P3][正确性] src/modules/skillRunner/run/skillRunnerForegroundContinuation.ts:859-866 —— 步定位用 provider 返回的 requestId，空值会命中“尚未分配 requestId”的步
- 证据：

```
  const stepIndex = args.sequenceState.steps.findIndex(
```

- 分析：步索引完全依赖 `args.result.requestId`；当它为空串而序列中存在尚未 request-created（`step.requestId` 为空）的步时，`findIndex` 会命中该步，随后用它写 `result.fetched`（:867-881）并作为 `acceptCompletedSequenceStep` 的 stepIndex，即对错误的步执行 apply 流程。调用方 `continueSkillRunnerForegroundRunNow` 本身已持有可信 `requestId`，无需依赖 provider 回填字段。
- 建议：把调用方已知的 `requestId` 传入并用它定位（并在 `stepIndex < 0` 时保持现有早退），空值不得参与匹配。
- 置信度：中（触发前提是 provider 结果缺 requestId，本切片外无法验证其返回契约）

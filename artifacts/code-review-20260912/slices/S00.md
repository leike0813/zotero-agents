## B. Findings

### F1 [P2][正确性] scripts/sync-gitee-release.ts:83 —— 空 release body 会让 Gitee 同步整体失败

- 证据：
```
      const value = argv[i + 1];
      if (!value || value.startsWith("--")) {
        throw new Error(`${entry} requires a value`);
      }
```
- 分析：调用方 `scripts/sync-gitee-publication.ts:256-259` 固定传 `"--body", args.metadata.body || ""`。当 GitHub release（插件 tag 或 `release` 元数据）的 `body` 为空/缺失时，argv 中 `--body` 的下一个元素是空串，`!value` 为真 → 抛 `--body requires a value`，整个 `sync:gitee-release` 中止，后续资产上传/校验全部不执行。触发条件明确（存在无正文的 release 即可复现），且是静默环境差异型故障。同一函数还拒绝以 `--` 开头的值，正文以 `--` 开头也会误判。
- 建议：对 `--body` 允许空串（例如仅当 `value === undefined` 才报缺失，或对 `--body` 使用 `argv.slice` 直接取值），必要时改用 `--body-file`/环境变量传正文。
- 置信度：高

### F2 [P2][可移植性] scripts/e2e-single-markdown-live.ts:59 —— 用 `URL.pathname` 推导仓库根，Windows/含转义字符路径下会错

- 证据：
```
function projectRoot() {
  return path.resolve(path.dirname(new URL(import.meta.url).pathname), "..");
}
```
- 分析：`URL.pathname` 返回的是百分号编码路径，且在 Windows 上形如 `/C:/Users/...`，`path.resolve`/`path.dirname` 会得到错误根目录（`path.dirname` 只按当前平台分隔符切分）；同一模式在 `scripts/inspect-single-markdown-request.ts:38-40` 重复出现。切片内其它脚本（`build-help-docs.ts:39`、`inspect-literature-analysis.ts:39-43`）统一使用 `fileURLToPath`，此处属不一致写法。触发条件：在 Windows 运行，或 checkout 路径含空格/`%`/非 ASCII。影响：脚本指向错误目录，随后的 fixture 读取/`process.chdir` 失败。
- 建议：两处改用 `path.dirname(fileURLToPath(import.meta.url))`。
- 置信度：高（机制确定；实际影响仅限开发工具）

### F3 [P3][健壮性] scripts/run-zotero-full-suite.ts:33 —— 只监听 `exit`，spawn 失败时永不 settle

- 证据：
```
  const child = spawnNpm(["run", step.script]);
  const exitCode = await new Promise<number>((resolve) => {
    child.on("exit", (code) => {
      resolve(typeof code === "number" ? code : 1);
    });
  });
```
- 分析：`spawn` 失败（可执行文件缺失、EACCES、cwd 失效）只会触发 `error` 事件，不会触发 `exit`，因此 Promise 永挂起，`main()` 不再推进，包装脚本在 CI 中会一直等到 job 级超时而不是快速失败。同切片的 `scripts/run-ci-gate.ts:20-26` 正是 `error`/`exit` 双分支写法，说明这是遗漏而非设计。
- 建议：加 `child.on("error", () => resolve(1));`。
- 置信度：中（代码路径确定，触发需要 spawn 失败）

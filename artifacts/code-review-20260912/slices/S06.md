### F1 [P2][信任边界] src/modules/hostBridgeCapabilityRegistry.ts:1790 —— 调用方可控的 topicId 未净化即拼入落盘文件名，可越出 bounded-output 目录写文件

- 证据：
```
      displayName: `synthesis-review-input-${String(topic.topic_id || input.topicId || input.topic_id || "topic")}.json`,
```
```
  const localPath = joinPath(exportRoot, args.displayName);
```
- 分析：`input` 是 Host Bridge 能力入参（MCP/CLI 调用方完全可控），当 synthesis 返回体里没有 `topic.topic_id` 时，回退链会直接取用调用方的 `input.topicId/input.topic_id` 作为文件名片段。`registerBoundedOutputFile` 仅做 `joinPath(exportRoot, displayName)` 后调用 `writeRuntimeBytes`，而 `writeRuntimeBytes` 会 `await ensureRuntimeDirectory(parentPath(path))` 递归创建父目录——即既不校验段、也不拒绝 `..`，`displayName` 中的 `../` 会真实解析并越过 `tmpDir/host-bridge-exports/bounded-output/<ts>-<rand>/`，逐级向上到任意位置（`.json` 后缀与 `synthesis-review-input-` 前缀不足以限制最终 basename）。可达路径：调用 `topics.get_review_input`（无需 write 审批）→ synthesis 结果缺 `topic.topic_id` → 断言失败即写入调用方指定路径。影响：以 Zotero 进程身份在任意可写目录创建目录并覆盖 `.json` 文件（如本插件自己的状态/日志 JSON、其他插件配置）。注意：若 `utils/path.joinPath` 是「拒绝含 `..` 的入参」而不是「解析 `..`」，则该洞不成立；代码库其他写路径（`safeWorkflowProductExportPath`、zip 名 `replace(/[^A-Za-z0-9._-]+/g,"-")`）都显式做了 basename/字符过滤，此处是唯一一处直接插值。

- 置信度：中（依赖 `joinPath` 对 `..` 的处理方式）

### F2 [P2][错误处理] src/modules/runtimePersistence.ts:1967 —— 回滚失败会抛出新错误，丢掉导致回滚的原始错误

- 证据：
```
        await moveRuntimePath({
          sourcePath: backupDir,
          targetPath: targetDir,
        });
```
- 分析：位于 `copyRuntimeTree` 的 `catch (error)` 分支内（1967 起），用于把 `backupDir` 恢复回 `targetDir`。该 `moveRuntimePath` 未被 try/catch 包裹，一旦恢复失败（backup 被占用/已被删、目标路径出现新目录、跨设备等），抛出的是 move 的错误，而真正触发回滚的原始 `error`（1976 行 `throw error` 永远执行不到）被顶掉；此时现场是「targetDir 已被删、backupDir 仍在」的半提交状态，而报错信息只描述恢复动作，排障者拿不到根因。触发条件：复制阶段任一步失败（源文件缺失、权限、空间不足）且随后恢复也失败。
- 建议：把恢复动作包在 try/catch 中，恢复失败时以 `new Error(...)` 携带 `{ cause: error }` 或 `AggregateError([error, restoreError])` 抛出；至少保证主错误一定被抛出。
- 置信度：高

### F3 [P3][并发] src/modules/runtimeLogManager.ts:914 —— flush 可能在最新写入被标脏后直接返回，且定时器已被清掉

- 证据：
```
  if (inFlightSave) {
    await inFlightSave;
    return;
  }
```
- 分析：`flushRuntimeLogsPersistence()`（1211）先 `clearPersistTimers()` 再 `drainRuntimeLogPersistence()`。若在这之前 `inFlightSave` 对应的 `while (persistenceDirty && durableRevision < changeRevision)` 循环已经因「当时不脏」退出并 resolve，但 `finally { inFlightSave = null; ... }` 尚未作为微任务续体执行，而此时另一条微任务链上的 `appendRuntimeLog` 把 `persistenceDirty` 重新置为 true，则 flush 走 914 行的早退分支：只 await 那个已 resolve 的 Promise 就返回，既没有写盘，也没有重新排定 timer（入口已 `clearPersistTimers()`）。结果是最新条目只在「下一次 append」时才落盘；若 flush 发生在插件 shutdown/unload 的最后一步，最后若干条日志永久丢失。窗口很窄（一个微任务序），但 `flush` 的语义就是「立即持久化」，属于契约被破坏。
- 建议：早退分支 await 后复查 `persistenceDirty && durableRevision < changeRevision`，成立则重入写盘（或让 flush 循环直到 `durableRevision === changeRevision`）；早退前也不要无条件清 timer。
- 置信度：低

### F4 [P3][错误处理] src/modules/runtimeLogManager.ts:934 —— 日志落盘失败被完全吞掉，且不再排定重试

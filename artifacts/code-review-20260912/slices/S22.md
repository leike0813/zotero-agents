## B. Findings

### F1 [P2][并发/资源] rust/acp-ws-bridge/src/main.rs:595-609 —— 非 Windows 平台不终止后端子进程，连接关闭只会给 stdin 发 EOF
- 证据：
```rust
    #[cfg(not(windows))]
    {
        let _ = pid;
    }
```
- 分析：唯一收尾路径是 `handle_connection` 末尾的 `terminate_child(child_pid)`（989），Windows 分支执行 `taskkill /PID /T /F`，非 Windows 分支为空实现。子进程句柄已被 wait 线程 move 走（853-880），没有任何 `child.kill()`。触发条件：客户端关闭 WS（或帧读失败）时后端进程不响应 stdin EOF（977 只做 `drop(child_stdin)`）；此时子进程继续运行、wait 线程永久阻塞在 `child.wait()`，并持有 writer Arc 与子进程 stdout/stderr 管道句柄。影响：每个异常断开的连接都可能留下一个存活后端进程 + 一个泄漏线程（macOS/Linux 是发布平台之一）。
- 建议：非 Windows 分支实现等价终止（对 pid 发 SIGTERM/SIGKILL，或在连接关闭时通过共享状态让持有 `Child` 的线程调用 `kill()`），把连接关闭当作显式的取消信号传播。
- 置信度：中（代码事实确定；实际泄漏取决于后端是否响应 stdin EOF）

### F2 [P2][信任边界] rust/acp-ws-bridge/src/main.rs:661-672 —— spawn argv 明文写入审计文件，脱敏只按对象 key 匹配，字符串数组元素永远不脱敏
- 证据：
```rust
        json!({
            "command": &request.command,
            "argCount": request.args.len(),
            "args": &request.args,
```
```rust
        for (key, value) in source {
            record.insert(key, sanitize_json_value(value, None));
        }
```
- 分析：`sanitize_json_value` 仅当“对象 key”命中 `is_sensitive_key` 时才替换（110-146）；`args` 是字符串数组，元素以 `key=None` 递归，`--token xxx`、`--api-key=sk-…`、`Authorization: …` 之类内容原样落入 `bridge.ndjson`。stdin 文本帧走 `sanitize_text_preview`，也只对 `bearer <x>` 形式脱敏（162-165），`Authorization: <token>` 同样漏出。触发条件：任何把凭据放在 argv/文本行里的 spawn（CLI agent 常见）。影响：秘密持久化到审计诊断文件，可能随后续诊断一起外传。
- 建议：对 `args` 做逐项模式脱敏（`--key value` / `key=value` 成对处理），或只记录命令基名 + argCount；stdin preview 增加常见认证头正则脱敏。
- 置信度：中（脱敏机制确实只覆盖对象 key；是否实际泄漏取决于调用方是否把秘密放进 argv）

### F3 [P3][性能/容量] rust/acp-ws-bridge/src/main.rs:216-235 —— 审计文件每次事件 open/append/close，且无大小上限；每个 8KB 输出块至少 3 次写入并附 512 字符预览
- 证据：
```rust
    match OpenOptions::new()
        .create(true)
        .append(true)
        .open(&state.path)
```
- 分析：`append_audit_event` 每条事件都重新打开文件（216）；stdout 线程每读一块调用 `child_stdout_chunk_read` + `child_stdout_frame_sent`（732/754），stderr 同理（791/822），即每个 8KB 块 2-3 次 open/write/close，其中两次带 512 字符 preview。审计文件只追加、无轮转与大小上限（`state.seq` 只增不减）。触发条件：长时间运行、产出量大的后端。影响：磁盘无界增长 + 子进程输出热路径上的系统调用放大。
- 建议：单连接内保持文件句柄（或在 AuditState 内缓存 `File`），preview 采样/限流，并按大小轮转。
- 置信度：高（代码事实）

### F4 [P2][正确性] packages/synthesis-repository/src/durableBundleImport.ts:512-519 —— domain state 只做 UPDATE，singleton 行不存在时静默不写，import 仍然提交
- 证据：
```ts
  db.run(
    "UPDATE synt_concept_application_state SET manifest_hash=@hash,index_stale=1,updated_at=@now WHERE singleton_id=1",
    { hash: manifestHash, now },
  );
```
- 分析：`ensureSynthesisConceptKbApplicationRepositorySchema`/topicGraph/tagVocabulary/referenceRefresh 都只建表、不插入 singleton 行（首次 `getSynthesis*ApplicationState` 返回 null）。整库恢复（durable bundle import）会命中该场景：`applyEntry` 已把 concept/tag/topic/reference 行写入并提交，但四张 state 表的 manifest_hash / index_stale 从未落库。后果一：`activeBases.conceptManifest` 仍为 null，后续 `replaceSynthesisConceptKbState({expectedManifestHash: null})` 的 CAS 会通过并把刚导入的数据整表删除；后果二：导入声称建立了 manifest 基线，实际没有任何行记录它。对照同函数下方 topic 分支用 `INSERT OR REPLACE` 兜底（533-564），说明缺行是应当处理的。
- 建议：这四处改为 UPSERT（存在则保留原有 title/路径等列，不存在则插入默认行），或在缺行时显式抛稳定错误而不是静默跳过。
- 置信度：中高

### F5 [P2][契约] packages/synthesis-repository/src/durableBundleImport.ts:409-418 —— payload 表主键取 `entry.entity_id`，capture 却按 payload 内部 id 重建 entityId，二者无一致性校验
- 证据：
```ts
      `INSERT OR REPLACE INTO synt_topic_interest_metadata(topic_id,payload_json,updated_at)
       VALUES(@id,@payload,@updated_at)`,
      {
        id: entry.entity_id,
        payload: json(entry.data),
```
- 分析：读侧 `captureSynthesisDurableBundleRepositoryState` 用 payload 内字段作为草稿身份：`draft("topic_interest_metadata", clean(data.topicId), data, …)`（durableBundle.ts:219-231，hint/effect 同形）。若 `entry.entity_id !== data.<idField>`，表内主键与基线身份分裂：同步索引认为实体 A 已同步，而基线导出的是 B，diff 会反复不收敛。更严重的是 `draft()` 对空 entityId 直接抛错（durableBundle.ts:104），而 `applyEntry` 对 `entry.data` 不做任何字段校验——一个缺少 `topicId` 的 envelope 会成功提交，随后任何 `captureDurableBundleState`/`captureDurableImportState` 都抛 `repository_durable_entity_id_invalid`，且没有回滚/修复路径，等于把该库的 capture 打死。
- 建议：写入前校验 `entry.entity_id === clean(entry.data.<idField>)` 且 payload 含必需身份字段，不满足则整笔事务回滚并返回稳定错误码；或统一以 `entry.entity_id` 为准并在 capture 侧读同一列。
- 置信度：中

### F6 [P2][契约] packages/synthesis-repository/src/conceptKb.ts:368（同形：topicGraph.ts:224）—— schema meta 无条件 INSERT OR REPLACE，缺少其它模块都有的版本校验
- 证据：
```ts
  db.run(
    `INSERT OR REPLACE INTO synt_schema_meta(key,value) VALUES(@key,@value)`,
    {
      key: SYNTHESIS_CONCEPT_KB_APPLICATION_REPOSITORY_SCHEMA_META_KEY,
      value: SYNTHESIS_CONCEPT_KB_APPLICATION_REPOSITORY_SCHEMA_VERSION,
    },
  );
```
- 分析：`citationGraph.ts:425-435` 会先读 meta 并在未知版本时抛 `repository_citation_graph_application_schema_unsupported`；`referenceRefresh.ts:317-328`、`tagVocabulary.ts:333-340`、`durableBundleImport.ts:204-211` 都是“先 INSERT OR IGNORE 再读回比对，不匹配即抛”。conceptKb 与 topicGraph 没有该守卫：旧二进制（或回滚后的版本）打开新版本写过的库时，会把 meta 静默改写为旧版本号并继续在结构可能已变化的表上读写，之后新版本读到的 meta 也被降级，无法再触发任何“版本不支持”保护。
- 建议：与 citationGraph 一致——先读 meta，`current && current !== VERSION` 时抛稳定错误码，再写入。
- 置信度：中

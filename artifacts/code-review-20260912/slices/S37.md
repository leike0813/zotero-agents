### F1 [P2][并发] profiles/hermes/zotero-librarian/scripts/zotero_librarian_service.py:381 —— 写事务跨 `call_bridge` 子进程持有，且子进程无超时
- 证据：
  ```python
  with conn:
      for row in rows:
          data = unwrap(call_bridge(args.bridge, ["run", "get", row["run_id"]], args.profile_prefix))
  ```
  （`workflow_catalog_refresh` 同形：`:345` `with conn:` + `:357` `detail = unwrap(call_bridge(...))`；`call_bridge` 在 `:129` 用 `subprocess.run(...)`，无 `timeout`）
- 分析：`sqlite3` 在首个 DML 上隐式开事务；`run_watch`/`workflow_catalog_refresh` 一旦发生首次 UPDATE/INSERT，事务保持到 `with` 退出，而循环内每个未终态 run / 每个变更 workflow 都要 fork 一次 `zotero-bridge` 并等待其退出。若 bridge 卡住（无 timeout），写锁被无限期持有，其它命令（含 `index.refresh` 的批量写）会得到 `database is locked` 或长时间阻塞。属于典型“写者持锁做 IO”。
- 建议：把 bridge 调用收集到事务外（先读 row→批量取数→最后一次性 `executemany` 写），并给 `subprocess.run` 加 `timeout`。
- 置信度：高

### F1 [P2][正确性] src/dashboard/backendManagerApp.ts:425 —— refresh 结果按下标回写到可能已变形的 rows 数组，会把 A 行的 ACP 配置写到 B 行
- 证据：
```

425	      if (Number.isInteger(rowIndex) && state.rows[rowIndex]) {
426	        state.rows[rowIndex] = {
427	          ...state.rows[rowIndex],
```

- 分析：`refreshAcp(index)`（531-539）把 `rowIndex` 发给宿主，宿主在 action-result 里原样回传；客户端随后用这个下标直接写 `state.rows`。而下标并非稳定身份：`removeRow`（505-509 `state.rows.splice(index,1)`）、`addRow`（510-515 push）、以及 `applySnapshot`（391-393 `state.rows = ...map(cleanRow)` 整体重建）都会使同一 `rowIndex` 指向另一行。触发：对第 2 行点“刷新 ACP/模型缓存”，在宿主应答前删除第 1 行（或宿主推来一次新 snapshot），应答到达时 `payload.acp`（属于 backend X 的运行时选项）被写进 backend Y 的草稿行；`emitDraftChanged()` 随后把该草稿发回宿主，用户保存即把错误的 ACP 选项持久化到 Y。同一根因也让 `pendingAcpRows/pendingModelCacheRows`（202-203、531-548）在 splice 后指向错误行，出现“别的行在转圈”。

### F3 [P2][错误处理] src/jobQueue/manager.ts:703 —— drain 的续跑链只有 fulfill 分支：runOne 抛出即队列停摆并产生 unhandled rejection
- 证据：
```
703	      void this.runOne(nextJobId).then(() => {
704	        void this.drain();
705	        this.resolveIdleIfNeeded();
706	      });
```
- 分析：`runOne` 的 `try/finally` 只覆盖 394-650，catch 分支里的 `settleSkillRunnerRunAsFailed`（537、615）、`applySkillRunnerRunEvent`（579）、`runtime.Zotero.logError`（666，未包裹 try/catch）以及 try 之前的 `this.emitJobUpdated(job)`（377，回调由调用方提供）任何一处抛出，都让该 promise 以 reject 结束。此时 `.then` 回调被跳过 → 不再调用 `drain()`/`resolveIdleIfNeeded()`：若这是当时唯一在跑的作业，`pendingIds` 中的后续作业直到下一次 `enqueue` 才会被拾起，`waitForIdle()` 的等待者则永久挂起；同时产生无人处理的 rejection。
- 建议：改为 `.then(onDone, onError)` 或 `.catch()`，在错误路径仍执行 `drain()` + `resolveIdleIfNeeded()`，并把异常写入运行日志。
- 置信度：中

### F1 [P2][正确性] src/synthesis/components/reader/ReaderRegion.tsx:205 —— digest 结果解析挂在整区域重渲染上，重复请求相同负载时会卡在 loading

- 证据：
```
  const digestResult = selection.digestResult;
  const digestResultSignature = stableRegionSignature(digestResult);
  useLayoutEffect(() => {
    const result = digestResult;
    if (!result) return;
    setDigest((current) =>
      current?.loading ? { ...current, loading: false, result } : current,
    );
  }, [digestResultSignature, digestResult]);
```
配合外部 memo：
```
  (prev, next) =>
    prev.t === next.t &&
    prev.onAction === next.onAction &&
    prev.renderGraphIsland === next.renderGraphIsland &&
    equalBySignature(prev.selection, next.selection),
```
- 分析：modal 的“loading→resolved”跃迁只发生在该 effect 运行且 `digestResult` 变化时。`ReaderRegion` 被 `equalBySignature(selection)` 记忆化，而 `selection.digestResult` 是其一部分。触发路径：打开论文 X 的 digest（`selection.digestResult` 落为结果 A）→ 关闭 → 再次打开 X（本地 `setDigest({loading:true})`，但 controller 未把 `digestResult` 清空）→ 宿主返回内容与 A 逐字节相同的结果 A'。此时整 selection 的签名不变，memo 直接跳过重渲染，effect 因 deps（签名与对象内容）未变化也不运行，modal 永久停留在 loading。影响：同一篇论文的 digest 二次打开不可用（取决于 controller 是否在派发时清空 `digestResult`，见“假设”）。
- 建议：为 digest 请求引入单调递增的 request/message id（或每次派发时把 `digestResult` 置空），并把它纳入该 effect 的输入，而非依赖内容签名。
- 置信度：中（机制由代码确证；可达性依赖 controller 在两次请求之间保留 `digestResult`）

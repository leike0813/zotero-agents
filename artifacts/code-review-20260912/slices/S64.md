### F1 [P2][正确性] rust/synthesis-sidecar/crates/synthesis-repository/src/lib.rs:2003 —— 分页终止条件用的是「过滤后总数」，与未过滤的页查询不一致，导致 capture 静默少读行
- 证据：
```rust

    .query(
        "SELECT COUNT(*) AS total
         FROM synt_topic_application_state state
         JOIN synt_topic_application_projection projection
           ON projection.topic_id=state.topic_id
         WHERE EXISTS (...)")?;
let rows = self.query(
    "SELECT * FROM synt_topic_application_state
     ORDER BY updated_at DESC,topic_id ASC LIMIT ?1 OFFSET ?2", ...)?;
```
消费方（checkpoint 文件 543-558、734-741）：
```rust
let (states, total) = repository.list_topic_application_states(offset, 250)?;
...
offset = topic_bases.len();
if offset >= total { break; }
```
- 分析：`total` 统计的是「有 projection 且 discovery.source_paper_refs 非空」的行数（记为 Q），而分页读的是整个 `synt_topic_application_state`（行数记为 R，Q ≤ R）。循环以 `offset >= Q` 终止：当 R > 250 且 Q ≤ 250（例如 300 个 topic，其中 10 个有 paper refs）时，第一页读走 250 行后立即 break，剩余 50 行永不读取。影响：`capture_durable_bundle_state` 的 `topic_bases`/`aggregate_basis` 与 `capture_debug_projection` 的 `topic_ids` 都不是全表的确定性快照，durable 导出的 basis 会随「恰好有多少行带 paper refs」而变化，导入侧 CAS 比较与导出内容均受污染。循环不会死锁（因为 Q ≤ R，offset 必然推进到 Q），所以是静默少读而非挂死。
- 建议：让 `list_topic_application_states` 返回与页查询同源的 R（`SELECT COUNT(*) FROM synt_topic_application_state`），或改为「页返回条数 < limit 即结束」的循环条件；两处 capture 循环共用同一终止判据。
- 置信度：高（不一致语义可直接读出），对「少读后果严重度」的判断为中。

### F3 [P2][并发/健壮性] rust/synthesis-sidecar/crates/synthesis-repository/src/lib.rs:1574 —— 写事务没有 RAII 守卫，闭包 panic 会泄漏 BEGIN IMMEDIATE 与 `transaction_depth`
- 证据：
```rust
        self.transaction_depth += 1;
        let result = operation(self);
        self.transaction_depth -= 1;
```
（对照读事务有 Drop 守卫：`impl Drop for RepositoryReadTransaction`，lib.rs:427-433）
- 分析：`operation` 一旦 panic 展开，decrement 与 COMMIT/ROLLBACK 都不执行：连接仍处于 `BEGIN IMMEDIATE`（持有写锁，直到连接被 drop），`transaction_depth` 卡在非 0。此后同一 Repository 上所有 `transaction()` 都走 `transaction_nested` 分支（`self.transaction_depth == 0` 为假）→ 只发 SAVEPOINT 不再 COMMIT，写入静默不落盘；`close()` 也会以 `repository_sqlite_transaction_active` 失败。本仓库确实在 panic 边界上工作（`panicking_sql_observation_restores_the_previous_scope`，lib.rs:3979 用 `catch_unwind`），因此该不对称是可复现的鲁棒性缺口。
- 建议：仿 `RepositoryReadTransaction` 引入 Drop 守卫（记录 outer/nested 与 savepoint 名，Drop 时回滚并递减深度），或至少用 `std::panic::catch_unwind` 包裹 `operation` 后再统一提交/回滚。
- 置信度：高（代码路径确定），实际触发需闭包 panic，故定级 P2 而非 P1。

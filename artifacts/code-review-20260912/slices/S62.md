## B. Findings

### F1 [P1][并发] citation_graph.rs:371-381 — with_reader 在无 reader pool 时退化为持有 writer mutex
- 证据：`pub fn read(&self) -> Result<CitationGraphReadView, String> { let basis = self.repository.with_reader(|repository| { ... });` 以及 ports.rs:459-472 `with_reader` 的 fallback 分支：`let Some(readers) = &self.readers else { let repository = self.repository.lock() ...; return operation(&repository); };`
- 分析：当 application 构造时未指定 `new_with_readers`（典型 citation_graph::CitationGraphApplication::new 默认 `RepositoryPort::new`，不带 readers），`with_reader` 会直接 `lock()` writer mutex，与同时发生的 `with_writer`（commit_graph / promote_metrics / promote_layout）序列化。基线条款要求"短 reader transaction 重校验 basis"——但因为没有独立 reader，调用 `read()` 在 rebuild/commit 进行中会被阻塞，破坏"reader transaction 重校验"的并行预期。read_view 实际上没有独立 SQL transaction，直接同步持 writer 互斥区调用 SQL。
- 建议：`CitationGraphApplication::new` 应当通过 `RepositoryPort::new_with_readers(repository, N)` 创建 reader pool（runtime_service.rs:282-285 已使用 4-readers；CitationGraphApplication 测试也是 `new_with_readers`）；或在 ports.rs 中要求 with_reader 必须有 readers，缺失则编译期报错。
- 置信度：高

### F2 [P1][资源/锁] citation_graph.rs:696-701 — refresh_metrics 在 rebuild 完成后调用，期间持有 compute 句柄与 admission
- 证据：`let promoted_hash = match promotion { ... }; if let Err(error) = self.refresh_metrics_inner(&promoted_hash, &cancel, None) ...` refresh_metrics_inner（line 836-861）调用 `persistence::state(...)?`、`persistence::graph(...)?`（reader）、`compute.metrics(...)`（IO）、`persistence::promote_metrics(...)`（writer）。
- 分析：`_active` admission lease 在 line 538 `let (cancel, _active, ...)` 绑定并随函数返回 drop；该 lease 在 promotion 之后仍然 hold，直到 rebuild() 函数返回。若 promote_metrics 持 writer 互斥与外部 reader 冲突，metric refresh 阻塞所有 reader。条款"Host 读取/构建/计算不得持有 writer" 在 metrics 这条路径上不严格成立（refresh 内既 reader 又 writer）。
- 建议：metric refresh 应在 admission 释放后再启 background，或拆分为独立 admission 路径。
- 置信度：中

### F3 [P1][并发/契约] citation_graph.rs:802-834 — reserve 与 claim 不构成原子 CAS，prep 完可被抢占
- 证据：`fn reserve(&self) -> Result<Arc<AtomicBool>, CitationMutationStatus> { ... state.active = Some(Arc::clone(&cancel)); Ok(cancel) }`，`fn claim(&self, cancel: &Arc<AtomicBool>) -> Result<ActiveMutation<'_>, CitationMutationStatus> { if !state.active.as_ref().is_some_and(|active| Arc::ptr_eq(active, cancel)) { return Err(...); } Ok(ActiveMutation(self)) }`，中间路径：line 425-451 `prepare_rebuild` 在 reserve 后 `insert_operation(...)` 失败时 `drop(self.claim(&cancel))`（line 439）。
- 分析：CAS 实际由 `Arc::ptr_eq(active, cancel)` 实现——这是弱 CAS：若两个 thread 同时 reserve 且都拿到 active=cancel₁/cancel₂，第二个会拒绝。但 `prepare_rebuild` 完成 receipt insert 失败时，已经 cancel active 但 receipt 已不存在，无法被后续 cleanup（orphan running receipt）。该 orphan receipt 不会自动被 reconcile_restart 标注（runtime_public_maintenance_operation.rs:1067 的 reconcile 只 reconcile "running" 状态，"pending" 维持 continuation_required）。
- 建议：insert_operation 失败需将 receipt 标为 failed 再释放 admission；当前 orphan receipt 落在 "pending" 状态，会被 future reconcile 视为 continuation_required，但若它对应的 cancel atomic 已 drop 则不再 dispatch（语义一致）。
- 置信度：中

### F4 [P1][并发/契约] concept_kb.rs:541-787 — review/update/delete 重新 admit，但 ingest 同一线程已 mutate
- 证据：`pub fn review(&self, request: &ConceptReviewRequest) -> ConceptMutationResult { let mut snapshot = match self.repository.load() { ... }; ... let mut result = self.apply_replacement(...)`；`apply_replacement` 内 line 890 才 `self.mutations.admit()`。
- 分析：`review` 在 load → mutate → apply_replacement 内重新 admit；但 ingest_proposals 走 `replace_snapshot → apply_replacement`，不重新 admit——意味着两个 ingest 并发可同时通过 ingest_proposals 的 validation，但 apply_replacement 内部有 SingleFlight 串行。`update_display_text` 与 `delete_concepts` 不调用 ingest_proposals 但也不调用 apply_replacement，自行 mutate snapshot 后写入（line 717 `self.apply_replacement` 仍然走 mutate admission）。`apply_replacement` 才 admit，所以 review/update/delete 都共用 SingleFlight。admission 与 mutate 之间无 CAS：line 894-906 读完 state 后 write 之间无 basis check 之外的 lock；只有 `replace_with_receipt` 内 repository 自己做 CAS（write）。如果 repository 的 CAS 仅校验 manifest_hash 但应用层未把它与 admission 绑定，外部 cancellation（stop_admission）发生在 read 与 write 之间仍可能写入（"Stopping" 检查在 line 913，read 之后）。
- 建议：把 cancel-check 移到 admit 之后立刻做（已存在），但确认 read 与 write 之间不再被 cancel——目前 admit 后到 read 之间的窗口已被 line 913 覆盖；read 与 write 之间的窗口需要 SingleFlight lease 上的 cancel 触发 commit aborted 或 repository CAS 拒绝。
- 置信度：中

### F5 [P1][资源/锁] durable_bundle.rs:283-301 — acquire_with_runtime 在持 writer 期间调 canonical.recover_import
- 证据：`fn acquire_with_runtime(...) -> Result<Self, String> { ... let application = Self { ... }; application.reconcile_pending_import()?; Ok(application) }`；`fn reconcile_pending_import(&self) -> ... { let capture = self.repository.capture_import()?; let outcome = self.canonical.recover_import(capture.commit_receipt.as_ref())?; ... self.canonical.inspect_current(target)?; ... }`
- 分析：`capture_import` 走 `with_writer`（persistence.rs pattern），持 writer mutex；后续 `recover_import` 和 `inspect_current` 是 canonical store IO，可能耗时。在这条路径上 writer 持有整个 canonical IO 期间，其他 reader 都被阻塞。runtime 启动时此调用在 startup_step("application-compose") 之后立即执行，序列化延迟整个启动。
- 建议：把 reconcile_pending_import 拆出 startup，在 first request 时 lazy reconcile，或先 release writer mutex 再做 canonical IO。
- 置信度：中

### F6 [P2][错误处理] durable_bundle.rs:469-481, 498-507 — canonical.stage_import / apply_import 失败时主错误被 discard 吞
- 证据：`if !receipt.canonical.promotions.is_empty() && let Err(error) = self.canonical.stage_import(...) { let _ = self.canonical.discard_import(&receipt.receipt_id); return Err(error); }`，apply 同结构。
- 分析：discard 的返回值是 `_` 丢弃，外部调用方拿不到 canonical 是否真正清理成功（虽然底层 stage_import/discard_import 都 Result<(), String>）。不影响正确性，但主错误传播路径清晰：阶段错误仍由外层返回；后续若 discard 自身失败，orphan canonical stage 留下（与 receipt 一起），下次 reconcile_pending_import 应该回收。
- 建议：保留即可；可在 diagnostics 中记录 discard 的失败码便于 reconcile。
- 置信度：中

### F7 [P2][错误处理] related_items.rs:282-288 — exact_receipts 失败后未持久化失败 receipt，后续 batch 不再处理
- 证据：`if !exact_receipts(batch, &receipts) { summary.failed += batch.len(); summary.diagnostics.push("related_items_host_batch_invalid".into()); break; }`
- 分析：break 之后不再 `persist(current)`（line 374），host 实际已经 apply 了该 batch（不可逆）。`summary.failed` 仅是统计；effects 表中残留 `pending_external_write` 状态，下次 sync 仍会重新看到这些 edge（因 active_edge_ids 包含它们），但已经被 host apply 一次，会被 host 当 already_satisfied 返回，导致 `summary.existing += 1` 而非 `failed`。这是 known design（retry_owns_pending 测试通过），但 status 路径"applied → already_satisfied"在 repeat sync 时确实无法区分"本轮失败" vs "前次已 applied"；这造成 operation record 上的失败诊断与 effects 表不一致。
- 建议：在 receipts validation 失败时至少为该 batch 写入每条 plan 的 effect.status="needs_attention"，与 "not_found" 同路径；目前 break 让 effect 留在 pending。
- 置信度：低-中

### F8 [P2][panic 可达性] related_items.rs:372 — `unreachable!("receipt validation owns status")` 可被 host 越界 receipt 触发
- 证据：`_ => unreachable!("receipt validation owns status"),`
- 分析：`exact_receipts`（line 466-470）已校验 status 必为 "applied" | "already_satisfied" | "not_found" | "failed"，所以理论上不可达。但如果 host 端口被替换或测试 fixture 绕过校验，panic 会传播。设计上合理，但同等调用还有 workbench.rs:197 `unreachable!("active_review_tab validates the closed tab set")`，后者 active_review_tab 已经 `if matches!(tab, "reference_matching" | "topic_graph" | "concepts")` 守门，安全。related_items 这条更脆弱——仅 `exact_receipts` 校验依赖 status 集合，且 `exact_receipts` 调用在 line 282 已经发生，所以越界 status 在 line 282 之后被 catch；该 unreachable 实际安全，但仍标注以便 main reviewer 复核。修改一个 status 字符串即可让 exact_receipts 接受非法值。
- 建议：将 exact_receipts 的 status 集合与 unreachable 行共享 const，避免漂移。
- 置信度：中

### F9 [P2][契约] tag_audit.rs:307-317 — begin 同时 abandon 其他主机 runs，按 host_instance_id 过滤存在边界
- 证据：`repository.abandon_tag_audit_runs_for_other_hosts(request.library_id, &request.execution_identity.host_instance_id, &record.updated_at)?;` 和 `abandon_inactive_tag_audit_runs_for_host(request.library_id, &request.execution_identity.host_instance_id, &request.active_run_ids, &record.updated_at)?;`
- 分析：active_run_ids 由调用方提供；begin 不校验其真实性。若调用方传入 active_run_ids 含其他有效 runs（漏报），abandon_inactive 仅 abandon "不在 active_run_ids 内" 的当前 host runs——剩余 active runs 被保留。如果 host 重启后新的 begin 错过传入某 active_run_id（漏报），该 run 会被当 inactive abandon；但如果误传空 active_run_ids，所有当前 host 的 active runs 都会被 abandon。可能误关正在进行的同 host run。
- 建议：在 begin 之前要求 active_run_ids 必须真实反映当前 host 的所有 active runs（add 文档约束或运行时校验），或在 repository 层 enforce。
- 置信度：低-中

### F10 [P2][并发] webdav_sync.rs:731-740 — upload_export 二次 HEAD read 用 etag 比对，但 abort 可被 race
- 证据：`let current = self.host.read_text("HEAD.json").map_err(...)?; if current.etag != observed.etag { return Err(...); }`
- 分析：observed.etag 由 sync_once line 602 取得（line 685），中间经过 preview_import/apply_import/build_export 等 IO，耗时可能数十秒；这期间另一端可写 HEAD.json。新 read_text 用 etag 比对能 detect remote change，但仍写到 manifest 与各 assets；如果 remote 写入发生在第二次 read_text 之后与 HEAD.json 写入之前，HEAD 写入失败但 manifests 已上传。line 767-782 用 observed.etag 作 if_match，但 observed 在 sync_once 开始时取，可能 stale。
- 建议：上传 HEAD.json 前再做一次 read_text（with timeout）作为 final guard，或对每个 asset write_text 也带 etag if_match。
- 置信度：低

## C. 存疑（不足以判定为缺陷）

- citation_graph.rs:323-328 `operation_id` factory 闭合 `Arc<new(AtomicU64)>`，每个新 CitationGraphApplication 独立 ID 序列，跨实例不冲突但单个实例内单调递增——正常。
- knowledge_checkpoint.rs:286-303 `discard_import` 在 admission 之后获取 receipt lock，但 receipt lock 与 admission lock 顺序是先 admission 后 lock，无锁顺序问题；stop_admission 在 line 305 调用 admission.stop() 再 clear_receipt()，lock 顺序反向但因 clear_receipt 用 .lock() 直接置 None 而 stop 仅翻 accepting 标志，无 deadlock。
- webdav_sync.rs:286-290 `load_webdav_sync_state` 通过 state_transaction mutex 串行所有 state 读写（load 与 persist_patch 都重新拿），可正确序列化；与 runtime mutex 不重叠，无锁顺序问题。
- concept_kb.rs:1341-1365 `merge_concept_proposal` 跳过 self-relation 与 dangling target，无 cycle 检测（可能形成 relation cycle），但不在本次审计硬约束范围。

## B. Findings

### F1 [P1][正确性] legacy_ts_migration.rs:331-360 —— copy_direct_tables 把 legacy 列名直接拼到 main 端 INSERT
- 证据：
  ```rust
  for table in DIRECT_COPY_TABLES {
      let columns = table_columns_in(connection, "legacy", table)?;
      if columns.is_empty() { continue; }
      connection.execute(
          &format!("INSERT INTO main.{table}({columns}) SELECT {columns} FROM legacy.{table}"),
          [],
      )
  }
  ```
  以及 `classify_legacy_ts_schema:296` 已经为 `synt_topic_graph_node` 显式白名单 `planning_json` 漂移，说明 legacy schema 漂移是**已知的合法事件**。
- 分析：DIRECT_COPY_TABLES 含约 28 张表，**只有 `synt_topic_graph_node` 与 `synt_topic_discovery_hint` 在分类阶段有特殊列处理**。其余表若 legacy 列集合与 main schema 不一致（哪怕多一列），`format!` 拼出的 INSERT 会带 main schema 不存在的列名，SQLite 立刻 `SqliteError: no such column`，整个事务回滚——但 caller 收到的错误是底层 SqliteError，没有指向"legacy 列漂移"这一根因。
- 建议：DIRECT_COPY_TABLES 与 LEGACY_TABLES 共用同一份"接受列集合"；在 copy_direct_tables 里用 `main` 列与 `legacy` 列求交集后再格式化。
- 置信度：中

### F2 [P2][正确性] legacy_ts_migration.rs:556-568 —— copy_counts 漏检从 synt_artifact_sidecar 聚合出的 synt_reference_source
- 证据：
  ```rust
  fn copy_counts(connection: &Connection, table: &str, legacy_table: &str) -> Result<(), String> {
      let current: i64 = ... SELECT COUNT(*) FROM main.{table} ...;
      let legacy: i64 = ... SELECT COUNT(*) FROM legacy.{legacy_table} ...;
      if current == legacy { Ok(()) } else { Err("repository_legacy_fact_count_mismatch".into()) }
  }
  ```
  `copy_artifacts:451-458` 还会向 `synt_reference_source` 写一行 per distinct `paper_ref`，但 `copy_counts` 在调用点 705-714 只校验 `synt_reference_artifact` 而非 `synt_reference_source`。
- 分析：legacy 的 `synt_artifact_sidecar` 多行可能共享同一 paper_ref（artifact_type 不同），但只聚合出一个 source 行；如果 legacy 的 paper_ref 全集大于 main（copy 阶段漏了），`synt_reference_artifact` 行数还能对上，但 `synt_reference_source` 已丢失，且没有任何断言会响。
- 建议：在 `copy_counts` 列表里追加 `synt_reference_source` 校验，比较 legacy 端 `SELECT COUNT(DISTINCT source_ref)`。
- 置信度：中

### F3 [P2][一致性] library_snapshot_index.rs:142-225 —— promote 写完 singleton 与 generation 后才 DELETE 同行，但读路径无防御
- 证据：
  ```rust
  repository.connection()?.execute("UPDATE ... SET status='current' WHERE generation_id=?1 AND status='staging'", ...);
  repository.connection()?.execute("INSERT OR REPLACE INTO synt_library_snapshot_state(singleton_id,current_generation_id) VALUES(1,?1)", ...);
  repository.connection()?.execute("DELETE FROM synt_library_snapshot_generation WHERE generation_id<>?1", ...);
  ```
  `current_library_snapshot_generation()` 与 `list_current_library_snapshot_items()` 都是裸读，不带事务、不带"current 状态"的二次校验。
- 分析：写路径是原子的（同一事务），但**读路径只依赖 `synt_library_snapshot_state.current_generation_id` 一行**。如果 state 单例与 generations 表之间被外部干预（备份还原、VACUUM INTO、误删 state 行），读到的 generation_id 可能指向 `status='staging'` 或不存在的行；现有 reader 只会返回 `Ok(None)`，掩盖数据丢失。
- 建议：reader 入口处加 `WHERE status='current'` 过滤；并在 promote 末尾对"state→generation 链"做事务内自检。
- 置信度：中

### F4 [P2][契约] tag_audit.rs:813-835 —— update_tag_effect 单条接口不做 status/diagnostics 校验
- 证据：
  ```rust
  pub fn update_tag_effect(&mut self, effect_id: &str, status: &str, diagnostics_json: &str, occurred_at: &str, now: &str) -> Result<bool, String> {
      Ok(self.execute(
          "UPDATE synt_tag_effect SET status=?1,diagnostics_json=?2,occurred_at=?3,updated_at=?4 WHERE effect_id=?5",
          &[json!(status), json!(diagnostics_json), json!(occurred_at), json!(now), json!(effect_id)],
      )? > 0)
  }
  ```
  对照 `update_tag_effect_receipts:829-840` 显式白名单 status 与要求 diagnostics_json 为合法 JSON 数组。
- 分析：单条接口是更常用的入口，**缺少与批量接口一致的校验**。下游 caller 可塞任意 status（例如 `"cancelled"`、`"<script>"`），导致 `list_tag_effects`/导出路径出现 schema 外值；diagnostics_json 也可不传合法 JSON，下游解析崩溃风险集中在 reader 一侧。
- 建议：把 status 白名单与 JSON 校验抽到 `validate_tag_effect_receipt(&TagEffectReceiptRecord)`，两个 update 路径共享。
- 置信度：高

### F5 [P1][契约] tag_concept_topic_graph.rs:660-668、704-721、1280-1305 —— replace_* 直接写 state，绕过 stale 闸门
- 证据：
  ```rust
  replace_tag_candidate(repository, replacement)?;
  put_tag_state(repository, &replacement.state)?;   // state.index_stale 由 caller 决定
  ```
  `TagApplicationStateRecord.index_stale: i64` 默认 1，但 caller 可以塞 0；`ConceptKbReplacement.state` 与 `TopicGraphReplacement.state` 同样。
- 分析：index 闸门本应保证"替换 → 索引失效 → 重新 promote_index → 标记 stale=0"。`replace_*` 路径却把控制权交给 caller：caller 在 `replacement.state` 里写 `index_stale=0` 与任意 `index_json`，**`promote_*_index` 就不再被强制调用**，下游读到陈旧 index 但 state 假装新鲜。这是跨层的"投影层反向成为定义来源"风险（与 AGENTS.md 中页面约束同源）。
- 建议：replace_* 内部强制 `state.index_stale = 1`、`state.index_hash = ""`、`state.index_basis_hash = ""`、`state.index_json = "{}"`，丢弃 caller 在这三字段的输入。
- 置信度：中

### F6 [P2][性能] tag_concept_topic_graph.rs:463-563 —— refresh_topic_discovery_projections 是 O(P*H) 全表扫描，写事务内执行
- 证据：
  ```rust
  self.transaction(|repository| {
      let hints = repository.query("SELECT payload_json FROM synt_topic_discovery_hint ORDER BY hint_id", &[])?.into_iter().filter_map(|row| { ... }).collect();
      for mut projection in projections {
          ...
          let visible_hints = hints.iter().filter(|hint| { hint.get("topic_id")...cascade.contains(topic_id) }).filter_map(...).take(25).collect();
          ...
      }
  })
  ```
- 分析：每个 projection 都对全表 hints 做一次 filter_map（且 `filter_map` 在 `.take(25)` 之前，意思是所有匹配 hint 都先 mutate `open`/`rejected` 集合再丢弃多余项）。`synt_topic_discovery_hint` 没有 topic_id 索引（payload_json 是 JSON 字符串），每次 refresh 都是全扫描 × N projection。整个循环在写事务内执行——持有 writer 时阻塞其他读写。
- 建议：先 `SELECT topic_id, COUNT(*) FROM synt_topic_discovery_hint GROUP BY json_extract(payload_json,'$.topic_id')` 预分桶，每个 projection 只遍历自己桶；或将 refresh 拆批，每批小事务。
- 置信度：高

### F7 [P2][契约] tag_concept_topic_graph.rs:398-420 —— update_topic_discovery_hint_outcome 的 sticky screened_out 静默覆盖 caller
- 证据：
  ```rust
  let next_status = if status == "open"
      && object.get("status").and_then(Value::as_str) == Some("screened_out")
      && current_basis == basis_hash
  { "screened_out" } else { status };
  object.insert("status".into(), json!(next_status));
  ```
- 分析：caller 显式传 `"open"` 想解除 screened_out，但 basis_hash 没变——函数静默保留 `"screened_out"`，且 `Ok(Some(payload))` 返回的是更新后的 payload（看起来好像生效了）。依赖返回值判断是否生效的 host/agent 逻辑会误判。
- 建议：在 sticky 命中时返回 `Err("topic_discovery_hint_sticky_screened_out")` 让 caller 走显式 unscreen；或把 `requested_status` 与 `applied_status` 一并返回。
- 置信度：中

### F8 [P3][契约] worker_protocol_corpus_parity.rs:127-142 —— 用 case.id 子串匹配分发，多匹配场景无歧义控制
- 证据：
  ```rust
  let accepted = if case.id.contains("tag-entry") { tag_page(case.value) }
                 else if case.id.contains("concept-alias") { concept_alias_page(case.value) }
                 else { false };
  let _ = case.schema_ref;
  ```
- 分析：`CorpusCase.schema_ref` 已经在结构体里声明（`#[serde(rename_all = "camelCase")] schema_ref: String`），却被 `let _ = case.schema_ref;` 显式丢弃，改用脆弱的子串匹配。一个 case.id 同时含 `tag-entry` 与 `concept-alias` 子串（例如 `"tag-entry-extra-concept-alias"`）时永远走 tag_page 路径；新增 `tag-entry-v2` 也照样匹配，但 parity 结果不可区分"上游没传"与"上游传错 schema_ref"。
- 建议：用 `case.schema_ref` 做精确 dispatch（已经存在但未用），或在结构体里新增 `kind` 字段。
- 置信度：高

### F9 [P2][可维护性] library_snapshot_index.rs:48 —— valid_identity 与 schema 层约束职责重复
- 证据：
  ```rust
  fn valid_identity(value: &str) -> bool {
      !value.is_empty() && value.len() <= 512 && !value.chars().any(char::is_control)
  }
  ```
  `Repository::upsert_operation` 在 lib.rs:1621 已经复用 `validate_identity_part`；这里却重新定义一遍。
- 分析：`valid_identity` 只在三个公共方法入口出现，行为与 lib.rs 的 `validate_identity_part` 几乎一致但**不导出**，未来新增字段时容易漏加校验。控制字符的检查（`is_control`）也没下沉到 schema CHECK 约束，意味着 SQLite 直连写入（绕过应用层）仍然能塞入控制字符。
- 建议：复用 `validate_identity_part`（或抽到 `pub(crate)` 共享），并在 schema.sql 里对 generation_id/snapshot_id 加 `CHECK(no control chars)` 约束。
- 置信度：中

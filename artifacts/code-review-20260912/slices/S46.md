## B. Findings

### F1 [P1][并发] src/modules/assistant/publication/assistantWorkspacePublicationRuntime.ts:907 —— 在飞 flush 期间入队的 lane 因定时器已被清空且 flush 提前返回而永久滞留

- 证据：
```
907    if (this.flushing) return this.flushing;
908    const run = this.flushPending();
909    this.flushing = run;
```
```
1012    if (this.flushTimer) return;
1013    this.flushTimer = setTimeout(() => {
1014      this.flushTimer = null;
1015      void this.flush();
1016    }, 16);
```
- 分析：`flush()` 在入口就把 `flushTimer` 清成 null（L903-906），因此 flush 进行中（`flushing` 非空）时 `queue()` 会重新挂一个新定时器；该定时器回调先把 `flushTimer` 置 null 再调 `flush()`，而 `flush()` 因 `this.flushing` 为真直接返回，既没有取走 `this.pending` 里的新 lane，也没有重新排程。`flushPending()` 在 L1020-1021 已经快照并 `clear()` 了当时的 pending，所以新 lane 是彻底孤立：既不在本轮读取内，也没有定时器。`finally`（L913）只清 `flushing`，不检查 `pending`。触发条件：任意 `adapter.readOwnerRegions/readTranscriptPage` 慢于 16 ms（初始化/steady-state 全量读很常见），期间来一次 `schedule()`。影响：该次变更的 publication 不再发出，直到下一次 `queue()` 恰好又挂上定时器或有人显式调 `flush()`；若这是该 owner 的最后一个事件（例如 owner-control 终态、turn 结束），UI 会一直停在旧状态。
- 建议：定时器回调不要在 flush 前置空 token（或在 `flush()` 的 `flushing` 早退分支里重新排程一次）；更简单的是把「`flushing` 结束时若 `pending` 非空则再 `void this.flush()`」放进 L910-914 的 finally。
- 置信度：高

- 置信度：中

- 分析：`upsertTranscriptMirrorItem` 总是传 `newItem: true`，而 `applyAssistantTranscriptMirrorEvent` 对同一 itemId 是幂等 upsert（L206-209 只在缺失时 push id）。因此对已存在 itemId 的再次 upsert 会让 `transcriptItemCount` 比 `transcriptItemIds.length` 多计；反之 delete 路径只清 map/数组、不递减 count。计数与 id 数组是同一事件派生的两份状态，长期运行（tool-call 更新复用 itemId、条目被删除）后必然不一致，而 cardinality 是实时按 before/after 推导的（L357-362），只有 count 会漂移，消费方无法通过 cardinality 校正。

- 置信度：中

- 分析：该函数其余部分都做了防御（顶层非对象 return null、detail 的 JSON.parse 包在 try 内、文本长度有界），唯独 options 元素直接断言；元素为 `null`（JSON 里合法、稀疏数组序列化后也会出现）时 `entry.optionId` 抛 `TypeError: Cannot read properties of null`。该异常发生在构造 permission region payload 的路径上，会把一次畸形/异常权限请求升级为整个 publication（乃至初始化）失败，而不是降级为 `null`/空选项。同一行还缺 options 数量上限，畸形输入可构造超长数组参与投影。

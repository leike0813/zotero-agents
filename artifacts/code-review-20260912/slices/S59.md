### F1 [P2][正确性] rust/synthesis-sidecar/crates/synthesis-application/examples/typed_application_parity.rs:609 —— 共享原子计数器直接下标 `operation_ids`，fixture 供数不足即 panic（index out of bounds）

- 证据：
```

            operation_ids[operation_index_factory.fetch_add(1, Ordering::Relaxed)].clone()
        }),
```
- 分析：同一模式出现三处（`:608-610` 主流程、`:756-758` `run_fault`、`:909-911` 主流程工厂），且 `operation_index`（`:898`）是**跨 main/drain/5 个 fault 共用的同一计数器、从不重置**。而入口校验只要求 `corpus.operation_ids.len() < 2`（`:819`）。驱动实际至少发起 15 次 `topic.apply`（`:917-981`）+ 1 次 drain + 5 次 fault apply，只要 fixture 的 id 数少于累计调用次数，就在被测应用内部发生越界 panic（在 `run_drain` 里表现为线程 panic → `applying.join()` 失败 → 报成 `fixture_drain_failed`，掩盖真实原因）。对比同文件其它 fixture 索引点（`:365`、`:405`、`:957`、`:964`）都用 `ok_or("parity_fixture_invalid")?` 处理，此处是唯一无检查的取值，说明是遗漏而非有意。

### F2 [P2][并发] rust/synthesis-sidecar/crates/synthesis-application/examples/typed_application_parity.rs:622 —— `run_drain` 在 condvar 上无超时等待闸门，被测 apply 提前返回或 panic 会永久挂起

- 证据：
```
        drop(
            changed
                .wait_while(state, |state| !state.0)
                .map_err(|_| "fixture_drain_failed".to_owned())?,
        );
```
- 分析：闸门 `state.0 = true; changed.notify_all();` 只在 `DrainEngine::validate_manifest` 内设置（`:210-215`），即必须 apply 走到 manifest 校验阶段。若 `topic.apply` 在更早阶段返回（准入/参数校验失败）或 panic，待测线程结束后无人 notify，主线程在 `wait_while` 上**无限阻塞**——CI 变成挂死而不是失败。对照紧邻的 shutdown 等待（`:636-639`、`:651-653`）都用了 `recv_timeout`，可见此处缺超时是遗漏；同类缺陷会随被测代码回归而放大（越早返回越容易挂）。
- 建议：给闸门等待加超时（如 5s）并以 `applying.is_finished()`/`try_recv` 轮询兜底，超时后 join 线程并返回 `fixture_drain_failed`。
- 置信度：中（挂起路径成立；正常 fixture 下不触发）

### F3 [P3][错误处理] rust/synthesis-sidecar/crates/synthesis-application/examples/checkpoint_bundle_webdav_debug_application_parity.rs:192 —— 条件写比较用 `.ok()` 吞掉 etag 读取错误，把 IO 失败降级为 `conflict`

- 证据：
```
        if if_match.is_some_and(|expected| Self::etag(&path).ok().as_deref() != Some(expected)) {
```
- 分析：`etag` 在读取失败时返回 `Err("remote_read_failed:…")`（`:139`）。`.ok()` 把它变成 `None`，于是 `None != Some(expected)` 为真 → 直接返回 `status:"conflict"`。语义上“远端不可读”与“远端版本不匹配”被合并：WebDAV 同步应用会走冲突分支，parity 报告把 `conflict` 当成正常结果记录（`writes` 也不会追加），从而可能掩盖真实实现差异或本应上报的读取失败。同一文件的 `read_text`/`write_text` 返回路径都用 `?` 传播该错误，只有这里吞掉。
- 建议：改为 `let current = Self::etag(&path)?;` 后再比较，读取失败照常 `remote_read_failed` 上抛。
- 置信度：高（行为可逐字判定；影响仅限 dev 驱动）

### F4 [P3][正确性] rust/synthesis-sidecar/crates/synthesis-application/examples/citation_reference_application_parity.rs:335 —— id 池耗尽时静默返回常量 id，产生重复 operation id 而不是 fixture 错误

- 证据：
```
        ids.lock()
            .ok()
            .and_then(|mut ids| ids.pop_front())
            .unwrap_or_else(|| "fixture:id:exhausted".into())
```
- 分析：`operation_ids`/`preparation_ids` 的校验只要求 `len() >= 2`（`:380-381`），但本驱动对 citation 有 4 次重建、refresh/matching 各若干次 apply。一旦供数不足，后续所有调用拿到**同一个** `fixture:id:exhausted`：若应用按 operation id 做 upsert/去重，第二次写入会覆盖或触发冲突，报告里的 `replayCode`/`busy` 之类的期望值就会失真——即 parity 驱动会在“验证工具自身缺陷”下给出看似合法但错误的判定。另外 `ids.lock().ok()` 把互斥锁中毒也静默降级为同一常量。

- 置信度：中（机制确定；是否触发取决于 fixture 供数）

### F1 [P2][正确性] addon/content/components/custom-select.js:37-42 —— 单选下拉打开时会强关其它菜单的 DOM，却不复位其 `isOpen`，导致其它下拉必须点两次
- 证据：
```js
      if (isOpen) {
        // Close all other custom selects
        const allMenus = document.querySelectorAll(".custom-select-menu");
        allMenus.forEach(function (m) {
          m.classList.remove("open");
        });
```
- 分析：`createCustomSelect` 的每个实例把 `isOpen` 保存在闭包里；这里只移除其它菜单的 `open` class，兄弟实例的 `isOpen` 仍为 `true`。随后点击兄弟下拉的 trigger（`event.stopPropagation()` 阻止 document 处理器兜底）会走 `toggleMenu()` → `isOpen = !true = false` → 走 `closeMenu()` 分支，菜单保持关闭。触发路径：打开 A → 打开 B（A 被强关）→ 点 A，第一次点击无任何反应，需点两次才能重新展开。同一文件的 `createMultiSelect`（211-220 行）通过 `closeMenuAndApply()` 正确复位，证明这是单实例路径的遗漏。
- 建议：把“关闭其它下拉”统一为调用对方暴露的 `closeMenu`/`closeMenuAndApply`（或在 `closeMenu` 里同步复位被关者状态），不要直接改 DOM class。
- 置信度：高

### F2 [P3][正确性] addon/content/components/custom-select.js:132-135 —— `setValue` 用 label 文本反查选项元素，重名 label 会高亮错项
- 证据：
```js
          const matchedOpt = Array.from(opts).find(function (el) {
            return el.textContent === opt.label;
          });
          if (matchedOpt) matchedOpt.classList.add("selected");
```
- 分析：`selectedValue` 是按 `value` 匹配得到的，但高亮却按 `textContent`（即 `label`）匹配。两个选项 label 相同时（如不同 value 都显示同一个后端名/“Default”），`find` 命中的是第一个，UI 高亮与实际值不一致；`getValue()` 返回的却是第二个 value。
- 建议：给 option 元素加 `data-value`（或保存 `optionEl` 映射），按 value 定位。
- 置信度：中

### F3 [P3][契约] addon/content/components/custom-select.js:274-282 —— 多选组件只在“新增”时改变调用方数组，“移除”时改绑本地数组，别名语义不一致
- 证据：
```js
        if (checkbox.checked) {
          if (!currentValues.includes(toText(opt.value))) {
            currentValues.push(toText(opt.value));
          }
        } else {
          currentValues = currentValues.filter(function (v) {
            return v !== toText(opt.value);
          });
        }
```
- 分析：`setValue(vals)` 直接 `currentValues = vals || []` 持有调用方数组引用，因此勾选会**就地 push 修改调用方数组**，而取消勾选只改内部绑定，调用方数组保留过期项。调用方若同时持有该数组并直接读取（不经 `onChange`），会看到“加了没减”的不一致值；`onChange` 只在 `closeMenuAndApply` 触发，中途读取必然不一致。
- 建议：内部始终持有副本（`currentValues = [...(vals||[])]`），增删都走同一套不可变更新。
- 置信度：中

### F5 [P3][并发] addon/content/markdown-reader/index.html:1008-1009 —— 启动时同步调用 + 125ms 轮询会在 bridge 已就绪的常规路径下把文档加载两次
- 证据：
```js
      waitForBridge();
      bridgeTimer = setInterval(waitForBridge, BRIDGE_INTERVAL_MS);
```
- 分析：1008 行直接调用 `waitForBridge()`；此时 `bridgeTimer` 仍为 `null`，若 bridge 已存在，它无法清掉“尚不存在”的定时器，直接 `loadDocument("request")`（未 await）。1009 行随即注册 125ms 定时器，首跳（t=125ms）再次进入 `waitForBridge`，bridge 仍在 → `clearInterval` 后**再次** `loadDocument("request")`。结果：每次打开 reader 都发出两次 `bridge.requestDocument()`、两次 `renderInto`、两次 `buildOutline`、两次 `applySearch`。宿主 bridge 若带副作用（记日志/占用文件句柄）会被重复触发。
- 建议：先注册定时器再调用一次（或用 `let started=false` 门闩，`loadDocument` 只允许进入一次）。
- 置信度：高（逻辑确定；实际重复次数取决于 bridge 就绪时机，热路径为 2 次）

### F6 [P2][信任边界] tools/synthesis-index-harness/cli.ts:90-94 —— debug DB 安全守卫用字符串比较路径，大小写/符号链接别名可绕过，使 harness 直接写真实 Zotero/插件 DB
- 证据：
```js
  const debugDb = normalizeDbPath(options.debugDb);
  const real = [options.zoteroDb, options.pluginDb].map(normalizeDbPath);
  if (real.includes(debugDb)) {
    throw new Error("debug DB path must differ from Zotero DB and plugin DB");
  }
```
- 分析：`normalizeDbPath` 只是 `path.resolve`（72-74 行），不做 `realpath`，也不做平台大小写归一。在大小写不敏感文件系统（macOS/Windows 默认）上 `.../Zotero/zotero.sqlite` 与 `.../zotero/zotero.sqlite` 是同一文件却通过校验；把 debug 路径设为指向真实 DB 的符号链接同样通过。之后 `ensureDebugSchema`（`CREATE TABLE IF NOT EXISTS harness_*`）、`writeRun`（多条 INSERT + `BEGIN/COMMIT`）都会作用在真实库上，污染/破坏用户数据——这正是该校验存在的唯一目的。
- 建议：比较时用 `fs.realpathSync`（对已存在路径）+ 平台大小写归一（`process.platform` 判定后 `toLowerCase()`），并对不存在的 debug 路径比较其父目录 realpath + 文件名。
- 置信度：中（绕过条件明确，但需路径别名式调用）

### F7 [P3][正确性] tools/synthesis-index-harness/cli.ts:682-689 —— `normalizeDbPath("")` 等于 cwd，使“必填参数”校验成为死代码并给出误导性报错

### F8 [P3][性能] tools/synthesis-index-harness/cli.ts:335 —— `buildCanonicalInputs` 以“复制整个数组再追加”的方式累积分组，桶内规模大时是 O(n²)
- 证据：
```js
    byEffective.set(effective, [...(byEffective.get(effective) || []), raw]);
```
- 分析：同一形状在 358 行重复（`rawTitleGroups.set(key, [...(rawTitleGroups.get(key) || []), row])`），另有 383-388 行在 `physicalCanonicals.map` 内对 `rows` 再做一次 `filter`（O(P·R)）。快照工具会全库读取 `synt_raw_reference`，当大量引用解析到同一 canonical（正是去重 harness 的目标场景）时，单个桶的累积拷贝量约为 N²/2，直接放大 `snapshot`/`run` 的耗时与 GC 压力。
- 建议：改为 `push` 到已有数组（`const bucket = byEffective.get(k) ?? (byEffective.set(k, []), …)`），并把 383-388 行的计数改为一次 `Map<canonicalId, count>` 预统计。
- 置信度：中（复杂度确定；绝对耗时取决于数据规模）

### F9 [P3][并发] tools/synthesis-index-harness/cli.ts:570 —— `runId` 仅由毫秒时间戳生成，serve 模式下并发 `/api/run` 会撞主键并整体回滚
- 证据：
```js
  const runId = `cluster-run:${Date.now()}`;
```
- 分析：`serve` 的请求处理器（743 行）是并发的 async 回调，没有队列/互斥；`harness_run.run_id` 是 PRIMARY KEY。同一毫秒内的两次 `/api/run`（浏览器双击按钮即可）会让第二条 `INSERT INTO harness_run` 失败，`BEGIN…COMMIT` 脚本整体失败并返回 500，本次运行完全不落库。此外两个 sqlite3 子进程同时对同一 debug 库写事务时没有 `busy_timeout`，会额外出现 “database is locked”。
- 建议：runId 加随机后缀/`crypto.randomUUID()`，并对写操作做进程内串行（`serve` 内单队列）或在 sqlite 脚本头部加 `.timeout 5000`。
- 置信度：中

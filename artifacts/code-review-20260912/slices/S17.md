## B. Findings

### F1 [P1][正确性] packages/synthesis-application/src/topicCanonical.ts:228 —— pathId 生成非单射，不同 topicId 可撞同一路径身份
- 证据：
```
  const slug = identity
    .toLowerCase()
    .replace(/[^a-z0-9._-]+/g, "-")
    .replace(/^-+|-+$/g, "")
    .slice(0, 80);
```
- 分析：`canonicalSynthesisTopicPathId` 先小写、再把非 `[a-z0-9._-]` 字符折叠为 `-`，最后截断 80 字符，三者都会丢信息。`strictTopicId`（197-211 行）允许大写、空格及任意非控制字符，因此 `"Deep Learning"`、`"deep-learning"`、`"DEEP LEARNING"` 都是合法 topicId 却得到同一 `pathId="deep-learning"`；80 字符截断同理。该函数是 `SynthesisTopicCanonicalSnapshot.pathId`、`InspectResult.pathId` 的唯一定义来源，且 `rebuildSynthesisTopicCanonicalSnapshot` 只校验 `input.pathId === canonicalSynthesisTopicPathId(topicId)`，无法检测跨 topic 撞车。若 canonical store 以 pathId 组织资产（命名与字段语义如此），两个 topic 会互相覆盖/读到对方的 current 资产，随后 metadata envelope 的 `data.topic_id !== topicId` 校验使至少一方变为 invalid。
- 建议：使 pathId 带上完整 topicId 的哈希（例如 `slug + "-" + hash(topicId)`，或直接始终使用哈希，slug 仅作展示前缀），并保留向后兼容的读取映射。
- 置信度：高（函数非单射已证实；影响取决于 store 是否按 pathId 落盘，但该字段的用途命名明确）

### F2 [P2][正确性] packages/synthesis-application/src/conceptKbApplication.ts:102 —— shortHash 实际只有 5 个十六进制字符，id 碰撞概率被放大
- 证据：
```
const shortHash = (value: unknown) =>
  hashSynthesisEngineCanonicalJson(value).slice("sha256:".length, 12);
```
- 分析：`hashSynthesisEngineCanonicalJson` 返回 `"sha256:<64 hex>"`，前缀长度 7，因此 `slice(7, 12)` 只产出 5 个 hex（20 bit），而同一仓库其他投影层用的是 `slice(7, 31)`（24 hex）。该 shortHash 被 `synthesisConceptSenseId`、`synthesisConceptAliasId`、`synthesisConceptReviewId` 使用：aliasId 碰撞会让一个别名被静默挂到别的 concept（`mergeProposal` 445-463 只按 aliasId 去重）；senseId 碰撞会让不同定义共享同一 sense；reviewId 碰撞会让不同 review 互相吞并。20 bit 下生日碰撞量级约 1.2k 个 id。
- 建议：改为 `slice("sha256:".length, "sha256:".length + 24)`（或与 referenceProjection 的 24 hex 对齐），并在必要处把截断值升级为完整哈希。
- 置信度：高

### F6 [P2][正确性] packages/synthesis-application/src/topicGraphApplication.ts:655 —— 已 resolve 的 review 合并 provenance 后不计入 changed，单变更被静默丢弃
- 证据：
```
            reviews.set(reviewId, review);
            if (review.status === "open") reviewIds.push(reviewId);
```
- 分析：当同一 tuple 已存在 `previousReview` 且其 status 为 `approved`/`rejected` 时，新低置信 proposal 会构造 `{status: previousReview.status, provenance: mergeJson(...), evidenceRefs: mergeJson(...), updatedAt}` 并写回 `reviews`，但因为 status 不是 open，`reviewIds` 不增长。若本次 ingest 没有别的 node/edge/review 变更，689-695 行的 `!changedNodeIds.length && !changedEdgeIds.length && !reviewIds.length` 会返回 `unchanged`，整份内存快照被丢弃——被合并进来的 provenance/evidence 永远不会落库。

- 置信度：中高（逻辑确定；触发需已 resolve 的同 tuple review 再次出现且无其他变更）

### F7 [P2][错误处理] packages/synthesis-application/src/durableBundleApplication.ts:487 —— 数据已提交后清理失败会把整个导入报为失败
- 证据：
```
      await options.repository.clearDurableImportCommit(
        currentReceipt.receiptId,
      );
      return {
        status: "committed",
```
- 分析：`applyDurableImportState` 成功即意味着导入已经落库；紧接着的 `clearDurableImportCommit` 若抛错，`applyImport` 直接 reject，调用方（`webDavSyncApplication.executeSync` 的 catch）会把整次同步标成 `failed_retryable`，尽管本地数据已经提交、且内存 receipt 已在 405 行被清空（`receipt = null`），重试时既不能复用 receipt 也不能区分“未提交”与“已提交但残留收据”。这是典型的“清理路径失败覆盖主结果”语义缺陷。

- 置信度：中

### F8 [P2][性能] packages/synthesis-application/src/citationGraphApplication.ts:685 —— projectSlice 每层重复解析 rolesJson，且 frontier 空后仍空转扫描全边
- 证据：
```
      const roles = (() => {
        try {
          return JSON.parse(edge.rolesJson || "[]") as string[];
        } catch {
          return [];
        }
      })();
```
- 分析：`projectSlice` 的外层 `for (depth < request.depth)` 每轮都 `for (const edge of allEdges)`，并在内层逐边 `JSON.parse(edge.rolesJson)`；解析结果不缓存。更严重的是当 `frontier` 变为空集（邻域已全部展开或 `maxNodes` 已满）后没有 `break`，后续 depth 迭代仍完整扫描全部边并解析 roles。读接口每次都走这条路径，代价是 O(depth × |edges|) 次 JSON 解析 + 扫描，且对已探明的小邻域也付全额成本。判断：这属于可避免的重复分配，非正确性缺陷。
- 建议：进入 depth 循环前把 `rolesJson` 一次性解析成 `Map<edgeId,string[]>`；在 `frontier.size === 0 || selected.size >= request.maxNodes` 时 `break`。
- 置信度：中（性能影响取决于 depth 上界与图规模）

### F9 [P2][正确性] packages/synthesis-application/src/tagVocabularyApplication.ts:300 —— legacy 数字 bindings 让 staged 列表直接抛错，而迁移入口又依赖列表
- 证据：
```
  const values = JSON.parse(row.parentBindingsJson || "[]") as unknown[];
  if (values.some((value) => typeof value === "number")) {
    throw new Error("legacy_tag_bindings");
  }
```
- 分析：`listStaged`（538-540 行）对 `listTagStagedSuggestions()` 逐行调用 `stagedFromRecord`，任一记录带数字型 parentBindings 就整个列表抛 `legacy_tag_bindings`；`stage`/`updateStaged` 同样如此。唯一能把数字 id 解析为 `{libraryId,itemKey}` 的 `resolveLegacyStaged` 只在 `promote` 内被调用（860 行），而 `promote` 需要 `request.tags`，UI 又必须先通过 `listStaged` 才能选 tag。结果是 legacy 数据存在时 staged 编辑/迁移链路整体不可达，用户只能看到一个无上下文的错误。
- 建议：在存在 legacy bindings 时让 `listStaged` 走迁移模式（返回迁移后视图或先触发 `resolveLegacyStaged`），或在 `stagedFromRecord` 中把数字值降级为可展示的占位而不是整表抛错。
- 置信度：中（抛错分支确定；是否真有 legacy 落盘数据需仓库侧确认）

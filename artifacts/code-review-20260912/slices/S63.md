### F1 [P2][并发] rust/synthesis-sidecar/crates/synthesis-canonical-store/src/lib.rs:1272 —— 打开 store 时无条件删除 `.writer.lock`，使正在被其他 owner 持有的写者租约失效，破坏文件系统级写者互斥
- 证据：
  ```rust
  let _ = fs::remove_file(root.join(".writer.lock"));
  ```
  与 `acquire_writer` 的加锁方式（1326/1334）：
  ```rust
  let path = self.root.join(".writer.lock");
  match OpenOptions::new().create_new(true).write(true).open(&path) {
  ...
  fn release_writer(&self, lease: WriterLease) { drop(lease); self.writer.store(false, Ordering::Release); }
  ...
  impl Drop for WriterLease { fn drop(&mut self) { let _ = fs::remove_file(&self.path); } }
  ```
- 分析：`.writer.lock` 的“存在即持锁”是跨 owner/跨进程唯一互斥（`AtomicBool` 是每实例的，见测试 `independent_owners_share_the_filesystem_writer_admission`）。可达序列：`a = open(root)`；`a.acquire_writer()` 创建锁文件；再 `open(root)`（或第二个 owner 打开）执行到 1272 把该锁文件删除；此时 `b.acquire_writer()` 的 `create_new` 成功，于是 a、b 同时持锁。更糟的是 `WriterLease::drop` 无条件 `remove_file`：a 释放时会删除 b（或任意第三方）新建的锁文件（ABA），使互斥进一步被破坏，可能导致两个写者交错提交 canonical 事务。
- 建议：把残留锁清理与“持锁检测”分开——不要在 `open_root` 盲目删除；改为在锁存在时读取内容/所有者信息判定是否为陈旧锁（或使用 OS advisory lock/flock），并让 `WriterLease` 记录并校验自己创建的文件后才删除。
- 置信度：中（触发需在另一 writer 活跃期间再次 `open`；若部署保证单进程单次打开则影响降级）

### F2 [P2][性能] rust/synthesis-sidecar/crates/synthesis-citation-graph-build/src/lib.rs:441 —— 每条 reference 都对其 target 节点的 aliases 重新排序并去重，同一 target 被 K 条引用命中的总代价为 O(K² log K)
- 证据：
  ```rust
  node.aliases.extend(reference.target_aliases);
  node.aliases
      .sort_by(|left, right| compare_utf16(left, right));
  node.aliases.dedup();
  ```
  （位于 `compute_typed` 的 reference 循环内，该循环上界为协议 `GRAPH_BUILD_INPUT_SECTIONS` 的 references ≤ 1_250_000）
- 分析：`nodes.get_mut(&reference.target_id)` 命中已存在节点时，每命中一次就对不断增长的 `aliases` 做一次全量 `sort_by` + `dedup`。当某个高被引目标（常见于 library/外部引用）被 K 条 reference 累计写入别名时，成本近似 Σ i·log i = O(K²log K)；即使不发生增长，也是每命中一次 O(|aliases|) 的重排。热路径上有明确二次放大，且输入规模上限很大，构成可被单次请求触发放大的 CPU 热点。
- 建议：循环内仅 `extend` 收集，循环结束后对每个节点一次性去重排序；或使用 `BTreeSet`/增量合并。
- 置信度：中（依赖多条引用携带非空 `targetAliases` 才放大，但代价随 K 增长是确定的）

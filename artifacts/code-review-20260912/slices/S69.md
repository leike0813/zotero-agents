## B. Findings

### F1 [P2][资源/生命周期] rust/synthesis-sidecar/crates/synthesis-sidecar/src/runtime_server_loop.rs:220 —— `Drop` 只回收已结束的 handler，在途 handler 的 `JoinHandle` 被静默丢弃（线程 detach），无法保证 quiescence

- 证据：
```rust
impl Drop for SidecarTransport {
    fn drop(&mut self) {
        self.listener.take();
        self.connections.interrupt_all();
        reap_finished_handlers(&mut self.handlers, &mut self.handler_panicked);
    }
}
```
（`reap_finished_handlers` 只对 `is_finished()` 的 handle 做 `join()`，见 87-99 行；唯一真正 join 在途 handler 的路径是 `drain(deadline)`，见 210-217 行。）

- 分析：`Drop` 与 `drain` 的语义差异是可观测的：`drain` 会等到 deadline 并把 `pending_handlers` 交给上层；`Drop` 则在 `interrupt_all()` 之后立刻返回，未结束的 handler 线程继续运行并被 detach。触发条件是**非正常清理路径**——`runtime_service` 在早期 `return Err`/`?` 或 panic unwind 时直接 drop transport（没有先 `drain`）。此时每个在途闭包仍持有 `Arc<RequestContext>` 并在执行 `handle_connection`；`interrupt_all()` 只能解除 socket 读阻塞，无法解除 handler 内部对 storage/owner 的引用。若上层随后按清理顺序释放可能被引用的存储（§2："共享 deadline 未退出时不得关闭可能被引用的存储"），就失去了这层保护；同时被 detach 的线程 panic 不再可观测（`handler_panicked` 也丢失）。

- 建议：让 `Drop` 也走统一清理语义——在 `Drop` 内先 `interrupt_all()` 再 `drain(Instant::now() + 短deadline)`（或至少 `debug_assert!(handlers.is_empty())` + 诊断日志），使"transport 被销毁"与"handler 已静止"同义；避免出现两条释放路径。

- 置信度：中（缺陷机制与代码证据确定；实际后果取决于 `runtime_service` 的清理顺序，本切片未包含该文件）。

### F2 [P3][错误处理] src/modules/pluginStateStore/mutationAuthorityTable.ts:198 —— `expirePluginMutationAuthorityEntryEvidence` 不校验受影响行数，静默 no-op，与 `settle` 的 fail-loud 语义不一致

- 证据：
```ts
    db.run(
      `
        UPDATE plugin_mutation_authority
        SET state='identity_only', result_json='', last_accessed_at=@last_accessed_at
        WHERE scope=@scope AND operation_id=@operation_id AND state='terminal'
      `,
      { scope, operation_id: operationId, last_accessed_at: lastAccessedAt },
    );
    return getPluginMutationAuthorityEntry(scope, operationId);
```
（对照 `settlePluginMutationAuthorityEntry`：`if (changes !== 1) { throw new Error("plugin_mutation_authority_terminal_update_missing"); }`，180-183 行。）

- 分析：同表同类变更的两个入口对"0 行更新"采取相反策略：`settle` 认为 0 行是契约违反并抛错，`expire` 认为 0 行是正常结果（行不存在、或行不是 `terminal`）并原样回读返回。触发条件：对不存在、`started`、或已经 `identity_only` 的行调用 expire。影响：调用方若把"未抛错"当作"终态证据已按 §2 '重启遗留 started 归 unknown' 的语义转为 unknown"，会在行仍为 `terminal` 时继续后续流程（虽然返回值里能读到真实 state，但类型签名 `PluginMutationAuthorityEntry | null` 不表达"是否真的过期"，容易被忽略）。另外该路径未调用 `throwMutationAuthorityStorageFault(...)`，只通过内部 read 间接注入 "read" fault，fault 覆盖面与其余写路径不对称（需确认 `PluginMutationAuthorityStorageFaultForTests` 的取值集合是否全部覆盖）。

- 建议：与 `settle` 对齐——校验 `changes()`，或在返回类型上显式表达结果（如 `{ expired: boolean; entry: PluginMutationAuthorityEntry | null }`），让调用方无法把 no-op 误读为成功。

- 置信度：中（代码事实确定；"调用方误读"为判断，取决于 `zoteroHostMutationAuthority.ts` 的用法）。

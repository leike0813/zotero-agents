### F1 [P1][并发] src/modules/zoteroHost/zoteroHostNativeMutations.ts:426 —— replaceStoredAttachment 在文件系统 effect 前后未持锁，且 native saveTx 与磁盘移动非原子
- 证据：
```ts
    await args.admit(() => undefined, "effect");
    await moveRuntimePath({ sourcePath: storageRoot, targetPath: backupRoot });
    oldMoved = true;
    await moveRuntimePath({
      sourcePath: args.prepared.stagingDirectory,
      targetPath: storageRoot,
    });
```
- 分析：整个替换包含「rename 目录 → rename 新目录 → `saveTx` 更新 attachmentFilename」多步。若进程在 `oldMoved=true` 之后、第二次 rename 之前崩溃/被取消，磁盘上原本的附件目录只剩 `.replace-backup-*`，而 Zotero 数据库仍指向原路径，附件变为不可读且不会被任何恢复逻辑回收。仅在同一调用栈的 catch 里回滚不覆盖进程终止。`admit(() => undefined, "effect")` 只是占位，未把文件移动与 DB 写入放进同一事务/同一不可中断区。
- 建议：让备份目录带可识别前缀并在启动/下次操作时做孤儿备份扫描恢复；或在 finalize 之前不 rename 原目录（先 rename 新目录到同父目录临时名，saveTx 成功后再原子交换），最小化「无就绪文件」的时间窗。
- 置信度：中

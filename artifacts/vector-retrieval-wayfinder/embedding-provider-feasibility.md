# Embedding provider interface feasibility

Research for [研究本地与远程 embedding 接口及模型更换约束](https://github.com/leike0813/zotero-agents/issues/79). Checked against first-party documentation and source on **2026-10-04**. This is an interface and constraint survey, not a provider recommendation or a project benchmark. No embedding inference requests were made.

## Evidence labels

- **Verified** means the cited provider or model documentation states the behavior.
- **Unknown** means the reviewed interface does not promise the behavior; callers must not assume it.
- **Implication** is a design consequence inferred from verified interface facts, not a provider promise.

The small sample covers two local execution paths (Ollama's local HTTP service and the Sentence Transformers Python library) and two hosted APIs (OpenAI Embeddings and Cohere Embed v2). Model-level properties vary within each provider. OpenAI-compatible request shapes alone do not establish semantic, truncation, task-mode, normalization, or model identity compatibility.

## Confirmed first-release scope

This survey is scoped to embeddings used for metadata, existing Markdown full text, analysis artifacts, and canonical Topics. It excludes ordinary notes, PDF highlights/annotations, and conversation notes. Retrieval may return literature, evidence snippets, or Topics, with source type preserved so callers can distinguish them. Indexing is isolated by library: current library is the default scope, and cross-library retrieval requires an explicit scope. These are corpus and query-scope constraints, not a provider or model choice.

## Consequences for a provider contract

1. **Make embedding capabilities explicit.** An existing generic HTTP connection can carry JSON to an endpoint, but it does not describe embedding-specific semantics. At minimum the embedding capability needs an input mode (query/document or symmetric), model identity, requested/native dimension, truncation policy, vector representation, normalization behavior, result-to-input association, and cancellation/partial-failure semantics. This follows from the real API differences above; “OpenAI-compatible” only addresses some wire fields.
2. **Treat dimensions as a shape check, not a space identity.** Equal-length vectors do not establish that two models produce comparable coordinates. Query and document encoders need the matched pair required by the model's instructions. **Implication:** changes to model weights, task/prompt behavior, input preprocessing or dimensions that change emitted representations require a compatible new recipe and new or explicitly validated converted corpus vectors. Merely changing endpoint address, credentials or library/source filters does not establish a new coordinate space. Whether equivalent providers can share vectors, or a representation can be converted without rerunning inference, remains a contract decision rather than an automatic re-embedding rule.
3. **Persist the complete embedding recipe with the index.** Use provider and exact model identifier (and immutable local revision/digest where available), dimension, output type/precision, query/document mode and prompt, tokenizer/preprocessing/chunking revision, truncation behavior, and normalization. Record an observed output dimension too, so an endpoint drift or misconfiguration fails closed rather than silently mixing rows.
4. **Preserve item identity, not provider ordering assumptions.** OpenAI synchronous results expose indices; its Batch API explicitly warns output order can differ and provides `custom_id`. Cohere returns an embedding array matching the input count but does not document item IDs in the synchronous response schema. Keep the caller's stable item ID and source type attached through request/result association.
5. **Keep library and source scope explicit outside the vector recipe.** Store each item's library identity and source type alongside its indexed content. Default query scope should resolve to the current library; cross-library scope should only be applied when explicitly requested. A query can then include literature, evidence snippets, or Topics according to scope while retaining each result's source type. **Implication:** changing selected libraries or source-type filters changes the candidate set, not the embedding coordinate space, as long as content and embedding recipe are unchanged. This is separate from model/mode changes, which require a new index space.
6. **Separate model acquisition from inference.** Ollama pull and Hugging Face snapshot downloads are networked setup actions. Offline runtime requires the full model artifact, tokenizer/configuration, and executable inference environment to already exist locally. Sentence Transformers is a Python library; calling it inside the Zotero privileged JavaScript runtime would require a compatible bridge/service or another supported runtime. This last boundary is an implementation inference, not a claim that the project has already selected such a service.
7. **Keep secrets outside ordinary provider configuration.** Hosted API keys are bearer credentials. OpenAI explicitly says not to expose API keys in client-side code such as apps and recommends server-side secret storage. That is a material boundary for a Zotero plugin calling a hosted provider directly: the project needs a deliberate credential-owning host/service path. A local service URL is not itself a credential, but exposing a local inference service beyond loopback changes its trust boundary. The exact Zotero host API and credential-storage integration need a separate project implementation audit. [OpenAI authentication](https://developers.openai.com/api/reference/overview)
8. **Normalize transient behavior above the adapter.** Hosted providers have account-specific quotas and request errors; local providers expose runtime availability and resource failures. The common caller still needs bounded retries for retryable failures, respecting provider retry hints, explicit cancellation state, per-item outcome accounting, and idempotent resumption. The source docs do not establish one common cancellation/partial-success behavior.

## Evidence boundaries and residual unknowns

- This checks published API contracts and official model metadata only. No latency, throughput, quality, memory, storage, or Zotero-runtime benchmark was performed; promotional/reported benchmark scores are not project measurements.
- Published limits and model catalog entries can change. Recheck limits, accepted dimensions, and model IDs when implementing or deciding configuration.
- The reviewed synchronous endpoints do not all specify output ordering with equal precision, item-level failure, or remote cancellation. The implementation should model absent guarantees instead of filling them in from SDK behavior.
- Model-card language coverage does not prove retrieval quality for this project's Chinese Zotero library or cross-language use. A local quality corpus and evaluation policy are outside this fact survey.
- The confirmed included content classes do not define how existing full text or analysis artifacts become chunks, nor how canonical Topic payloads are projected to embedding input. Those are project content-contract questions; this survey treats chunking and preprocessing versions as index identity metadata.
- No project decision is made here about default provider, default model, batch workflow, model-download UX, secret storage, or index migration UX.

# 本地向量引擎与持久化已确认要求

本文件记录[引擎与持久化方案](https://github.com/leike0813/zotero-agents/issues/84)中已确认的规划要求。用户已采纳 SQLite／现有 Repository 持久化、Rust 硬范围内候选评分与精确重排路线；查询契约及非向量基础交付已完成。路线确定不表示向量存储已实现或生产验收已通过。

事实与候选能力见[选型输入](./vector-engine-selection-inputs.md)及[引擎可行性研究](./vector-engine-feasibility.md)。生命周期遵循[已完成的生命周期决议](./index-lifecycle-decisions.md)。

## 实验收束状态

用户同意在第十轮后结束开放式探索，并完成唯一的有界 Rust 最终批次。十轮研究的路线取舍见[选型收束结论](vector-engine-selection-conclusion.md)；最新证据见[最终批次结果](issue91-results.md)：2k／10k 八个配置通过，25k oracle 准备超时，四个查询配置未测。引擎路线按 Q8 定案；目标 25k、生产与七平台验收由既有实施票承接，不继续启动探索轮次。Q1–Q7 保持既有要求，实验预算不作为生产默认。

## Q1：精确基准与近似检索取舍

- 先以精确检索建立比对基准，使用实际切分后的语料；不能用“25k 篇各一个向量”代替全文负载。
- 若精确方案满足已确认的延迟和实测资源预算，优先采用它。
- 若不能满足，允许采用近似方案，但需测量相对精确基准的召回损失，再确认可接受程度。
- 两种方案都必须遵守库、标签、集合等硬范围以及来源失效规则。
- 检索策略留在内部，不增加调用方选择精确/近似的参数。

精确只表示向量距离排名，内容相关性仍取决于模型。近似方案是否符合质量要求需同时检查范围内向量召回及按文献/Topic 聚合后的实际结果，不能把引擎层召回当作所有消费结果的质量证明。

依据：[Q1 用户定案](https://github.com/leike0813/zotero-agents/issues/84#issuecomment-5980799313)。

## Q2：同一 Repository 数据库存储优先

- 优先将向量及关联派生记录存入现有 `synthesis.db`，继续由 Repository 管理。
- 向量、被索引的来源版本、片段定位和可见状态一起存储，便于原子发布或替换一个来源的完整片段。
- 复用现有事务、迁移、连接管理和备份机制。
- embedding 请求及耗时计算在事务外进行，写事务只负责保存或发布已完成结果。
- 如果选定引擎需要独立索引文件，让它承载可重建的加速结构；数据库保留有效向量和发布依据，重建加速结构无需再次请求 embedding。
- 数据库/备份规模及向量读写与现有业务的资源争用纳入实测；影响超出预算时，再评估由同一 Repository 管理独立存储文件。
- Zotero 和 canonical Topic 继续持有原始事实，索引记录的来源版本不能替代原 source owner 的事实及核验职责。

这是存储优先方案，尚未确定具体 schema 或引擎加速结构，不将同库当作已有性能证据。独立加速文件的发布、恢复和清理须遵循已确认生命周期，不能另设持久化或维护生命周期 owner。

依据：[Q2 用户定案](https://github.com/leike0813/zotero-agents/issues/84#issuecomment-5980849632)。

## Q3：首轮比较两条精确路线

| 方案 | 已确认验证目的 |
|---|---|
| SQLite 保存向量，Rust 精确计算距离 | 建立正确性和性能基准，评估复用现有依赖能否满足要求 |
| sqlite-vec，先固定 v0.1.9 验证 | 评估扩展的实际性能收益，以及过滤、事务与七平台集成是否适用 |

两者使用同一批向量、距离规则和查询范围，比较延迟、内存、增量更新、恢复及包体成本。基准方案已经达标时，扩展方案需要有明确收益才值得引入。

两条精确路线都不能达标时，再进入近似引擎比较，按 Q1 验证召回损失。先确定验证对象并建立具体验证票，最终引擎由结果决定。v0.1.9 是首轮固定验证版本，不代表已选为生产依赖。

依据：[Q3 用户定案](https://github.com/leike0813/zotero-agents/issues/84#issuecomment-5980898310)。

## Q4：首轮向量表示和距离规则

- 保存未量化的 float32 向量，每维 4 字节。
- 首轮统一使用余弦距离，比较向量方向的接近程度；两条路线采用一致的数值处理规则。
- 保留配置所要求的完整维度，不自动截断、降维或量化。
- 距离计算留在检索内部，不增加公共搜索参数。

本条作为首轮比较条件。模型预设仍需核实其距离要求，最终默认规则结合质量实测确认；不将余弦规则适用于参考模型的证据当作任意用户模型的质量保证。

依据：[Q4 用户定案](https://github.com/leike0813/zotero-agents/issues/84#issuecomment-5980936439)。

## Q5：分批保存，最后原子发布

- 初建/重建以 Repository 内部构建标识区分本次数据与正式数据。每批向量与对应完成记录在一个短事务中提交；embedding 在事务外执行，未完成的构建数据不参与搜索。
- 全部有效计划材料就绪且通过既有 promotion checkpoint 后，在一个短事务中切换正式索引引用，同时更新模型 ID、维度、编码要求、索引范围、就绪状态及查询依据。不替换整个 synthesis.db，不让写事务贯穿整个构建。
- 发布前失败或取消时语义搜索保持不可用。用户重试核验并复用已保存的有效进度，重启后不自动继续；完成记录不得领先于对应向量提交，恢复不得混合半个索引或重新启用已知失效片段。
- 普通增量在一个来源的完整片段组准备好后，以短事务整体替换该来源，其它可用来源继续参与搜索。
- 整体发布成功后清理旧数据；清理失败只报告待清理问题，不撤销发布或关闭已恢复的语义搜索。
- 构建标识只属于 Repository 内部实现，不增加公共接口或运行队列。既有 public maintenance owner 继续持有取消、重试及生命周期，过期/取消后的输出不得发布。

本条细化既有生命周期，不预先指定生产 schema 或扩展实现。两条候选路线均须验证实际事务、取消及重开边界；事务一致性不等同于保证掉电时每一笔最近提交都被保留。

依据：[Q5 用户定案](https://github.com/leike0813/zotero-agents/issues/84#issuecomment-5980983992)。

## Q6：按来源结构切分，实测选择大小和重叠量

- 全文和分析产物优先沿标题、段落等已有结构切分；过长段落再细分，保留原文范围，不跨来源拼接。
- 一篇文献的短元数据组成一个编码单元；超长内容仍按长度要求细分。
- Topic 按已有结构中的 section、条目组织编码，不将整个 Topic 一律压成一个向量，不混淆不同 section 的筛选范围。
- 片段长度适应模型能力并预留前缀空间。能够取得实际 tokenizer 时按 token 计量，否则采用明确的保守长度策略；不能将字符数当作精确 token 数。支持关闭自动截断的服务应关闭，超长内容继续切分。
- 验证无重叠与少量重叠对相关性、向量数及存储的影响；同一轮引擎比较使用完全相同的切分结果。
- 切分属于索引内部规则，不增加搜索参数。报告记录切分配置和实际向量数，最终默认值随参考模型及质量结果确认；当前不虚构固定片段长度或重叠比例。

上述规则适用于各种语言，中英文及跨语言作为主要质量验收；不改变模型 ID 身份及同模型兼容服务切换决议。Ollama 提供 truncate=false 超长报错，见[官方文档](https://docs.ollama.com/api/embed)。来源正文与位置仍遵循既有核验契约。

依据：[Q6 用户定案](https://github.com/leike0813/zotero-agents/issues/84#issuecomment-5981056562)。

## Q7：切分规则变化通过显式重建生效

- 索引保存建库时采用的切分规则和参数；日常增量使用同一套规则，避免新旧片段大小及重叠方式悄悄混用。
- 插件或模型预设更新不自动重建。当前规则仍可支持时，已有索引继续使用；采用新规则需通过 Home 的现有重建入口，完成后整体切换。
- 同一来源中，实际编码文本、模型、维度及编码要求均未变化的片段可复用向量；重新生成片段位置与分组记录，只编码真正变化的部分。
- 新程序无法支持旧规则时，明确提示需重建并暂停向量增强，独立词法搜索继续可用；不自动扫描或请求 embedding。
- 规则记录属于内部实现，不增加搜索参数，不要求用户管理多套历史索引。整体重建及发布前失败/取消的语义暂停规则保持。

本条不改变索引绑定模型 ID、不绑定供应商配置的决议。切分记录管理派生片段及有效进度，不重新引入模型版本证明或连接身份绑定。

依据：[Q7 用户定案](https://github.com/leike0813/zotero-agents/issues/84#issuecomment-5981076877)。

## Q8：采纳 SQLite＋Rust 实施路线

- 现有 Repository／SQLite 保存有效原向量、来源版本、定位、可见状态和发布依据，复用原有事务、迁移、连接与备份。
- Rust 在硬范围内评分候选，从有效原向量按契约重算距离、精确重排并聚合对象最佳片段；小范围保留完整精确路径。候选截断后的重排不保证全范围精确 top-k，不能补回遗漏对象或最佳片段。
- 归一化矩阵是可重建加速数据，重建无需重新 embedding；其身份、失效、发布、恢复和清理融入现有 basis／maintenance 生命周期。常驻／映射和文件组织由生产设计与资源实测落实。
- 首版不引入 sqlite-vec 或 Faiss 生产依赖；不新增公共精确／近似参数、持久化转发接口、事实源或维护 owner。
- 保留目标 25k。目标规模查询、真实独立语料和人工相关性、动态来源／basis、业务争用、并发、故障恢复、首次／冷态资源及七平台交付经 OpenSpec 交给既有实施验收票。
- 6400 候选、4096 完整精确阈值、1024 维及最终批次资源预算不直接成为生产默认。实际默认值与资源边界在实施验收前明确；失败携具体证据重新讨论，不自动延长研究、换引擎或降低目标。

依据：[Q8 最终决议](https://github.com/leike0813/zotero-agents/issues/84#issuecomment-6019346923)。本票以路线决策完成，生产达标单独验收。

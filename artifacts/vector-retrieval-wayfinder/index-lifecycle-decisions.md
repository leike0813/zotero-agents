# 检索索引生命周期已确认要求

本文件记录[索引初建、增量更新、失效与恢复](https://github.com/leike0813/zotero-agents/issues/82)的规划决议。仅已确认行为列入要求；具体 DTO/schema、任务与生产实现由后续 OpenSpec 承接，本文不表示已经运行模型或建立索引。

用户确认的 Q1–Q15 已汇总为[生命周期规划结论](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980714524)。

## 已有前提

- 初建/重建由用户明确启动；已有索引允许有界增量更新。启动、普通读取或打开 Home 不触发全库扫描。
- Zotero 与 canonical Topic owner 持有原始事实；Retrieval Application 在既有 Rust runtime 内持有派生表示、索引及查询，复用 Repository。Public maintenance operation 保持既有生命周期 owner。
- 当前 Synthesis 数据根只有一套正式向量索引及一次重建任务，不长期保存逐模型历史索引。
- 索引绑定模型 ID 及编码要求，不绑定供应商、地址、凭据或服务配置 ID。同模型兼容服务切换免重建。
- 模型 ID 或影响表示的维度/编码设置变化通过重建切换；期间保留旧索引数据并关闭语义检索，发布前失败/取消保持关闭，成功后一起发布模型/编码与索引并恢复语义检索。旧数据清理失败遵循 Q10，不撤销发布。重建额外空间计入预算，空间不足保留旧索引数据。
- 查询和构建可按用户指定顺序切换同模型兼容服务；查询每个服务最多一次且共用时间预算，构建每批含服务切换最多三次尝试。
- 单次 embedding 响应必须完整建立输入/向量唯一对应并通过数量、维度及有限数值校验；无效响应整体失败，不写入其中部分向量。其他成功批次保留，恢复不机械重做整个索引。
- 关闭增强或删除服务连接保留索引；恢复同模型兼容服务可复用仍兼容且就绪的索引。

模型、连接及响应规则的当前依据为 [provider 票结论](https://github.com/leike0813/zotero-agents/issues/81#issuecomment-5979998325)。查询结果的来源核验、正文定位、方法/覆盖/状态及游标依据遵循 [查询契约记录](./query-contract-decisions.md)，不以 Topic freshness 代替检索索引状态。

## Q1：成功 apply 后自动有界增量更新

- 只有已建立索引时，文献分析/digest 或 Topic apply 成功才触发后台增量工作。
- 处理本次明确变化、且属于现有索引纳入范围的来源或 Topic，不扫描全库、不扩大范围。
- 文献 digest 变化只更新该文献相关分析片段；Topic 变化只更新该 Topic 检索内容。每种来源继续按自身内容版本及定位要求核验。
- 后台编码不阻塞 apply 完成，索引更新失败不改变原操作的成功结果。Home 的索引管理区域展示待更新或失败。
- 尚未初建索引时，apply 不自动创建全库索引。
- 自动工作沿用既有 Retrieval Application 和维护 owner；不新增 Agent/工作流索引维护 interface，也不将 embedding 工作纳入 canonical apply 事务。

依据：[Q1 用户定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980084420)。

## Q2：普通变化的有界更新与来源退出

| 变化 | 已确认处理 |
|---|---|
| Zotero 中可可靠定位的新增、编辑或附件替换 | 对纳入范围内受影响的材料自动进行有界更新 |
| 已确认的删除、移入回收站或合并 | 旧来源退出检索；合并后保留条目按当前 Host facts 更新 |
| 外部编辑器修改 Markdown 文件 | 用户执行“更新索引”时检查指定范围；证据搜索同次读取并核验来源 |

首版不增加全库文件监听或定时扫描，外部新内容在索引刷新前可能无法召回。普通搜索不启动索引维护；来源读取和版本核验属于查询正确性，不能把这次读取当作已更新索引。

处理不得扩大索引范围，notifier 回调内不得扫描全库。删除来源退出检索不能只依赖客户端最终过滤；查询可见性与发布遵循 Q3/Q4，失效记录及物理清理由后续引擎持久化方案和实施规格承接，游标遵循已确认查询依据规则。

依据：[Q2 用户定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980164162)。观测能力和 Trash/merge 身份处理未知项见 [只读核查](./retrieval-change-observation-feasibility.md)，开发须验证实际通知及 Host 来源状态，不能把对象仍可解析当作它仍可检索的充分依据。

## Q3：已确认文本变化后的旧片段可见性

- 被索引内容确认变化后，受影响来源的旧片段暂停参与检索，更新成功后恢复。
- 仅影响变化来源；digest 改写不影响未变化的全文来源，也不使整篇文献或整套索引一律不可用。
- 更新失败时维持该来源待更新或失败状态，不重新启用已知过期片段。
- 可独立搜索当前材料的词法方法继续工作；通过既有 coverage / issues 说明向量覆盖缺口，不增加对象 stale 字段，也不推断 Topic freshness。
- 仅标签、收藏夹等筛选条件变化，且被编码文本未变时，不暂停向量检索或重新编码；硬范围按当前 Host facts 执行。

普通 notifier 信号及附件 item revision 不自动证明正文已变化；未可靠观察的外部修改仍遵循 Q2 和查询来源核验。模型重建期间保留旧正式索引不代表可以恢复某个已知变化或删除来源的旧片段。

依据：[Q3 用户定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980181939)。

## Q4：增量按来源发布，初建/整体重建整体发布

| 操作 | 已确认发布单位 |
|---|---|
| 增量更新 | 一个来源的全部片段完成并校验后一次替换，恢复该来源；其它来源无需等待 |
| 初建或整体重建 | 本轮计划内需编码的有效材料全部完成后整体发布；重建期间保留旧正式索引 |

编码期间发现来源再次变化时，不发布已过期结果，转为处理最新版本。多个来源的增量分别完成、分别恢复，某个来源失败不阻止其它完成来源发布。

整体重建仍有材料编码失败时，保留旧正式索引和此前完成的新索引工作，恢复后完成切换，不自动发布只完成部分材料的新正式索引。保留成功批次与允许检索是不同的完成条件；单请求响应、一个来源的片段整组、整轮重建分别校验和发布。

保留旧索引继续受 Q2/Q3 约束，不恢复已删除来源或已知过期片段。

依据：[Q4 用户定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980197622)。

## Q5：整体重建期间语义检索整体不可用

- 整体重建期间暂停当前 Synthesis 数据根的向量/语义检索，不使用旧正式索引服务查询，不为旧索引增量编码。
- 可独立执行的词法方法继续使用，通过既有 method / coverage / issues 说明增强不可用；没有可执行方法时为 unavailable。
- 纳入范围内的新变化由待发布的新索引承接，处理最新版本并排除已退出来源，不要求旧模型可用或同时进行双模型编码。
- 新索引完成 Q4 的校验及整体发布后恢复语义检索。
- 来源级增量仍按 Q3/Q4 只暂停变化来源，不因此关闭全部语义检索。
- 保留旧索引及新构建进度只属于数据保留，不承诺旧索引仍可查询。失败/取消后的语义恢复遵循 Q6。
- 向量/混合查询续页保持已确认方法及依据失效规则，不偷偷改为词法续页。

依据：[Q5 用户修订定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980407180)。该规则替代早期 provider Q3 及 Q4 中重建期间用旧索引服务查询的部分。

## Q6：整体重建失败或取消后保持语义检索不可用

- 整体重建在新索引发布前失败或取消后，不自动恢复旧模型/旧索引的语义检索，继续保持不可用；成功发布后的清理失败遵循 Q10。
- 保留已经成功完成的构建工作，用户通过既有重试路径完成重建；新索引完整校验并整体发布后才恢复语义检索。
- 复用成功工作需符合来源版本、模型 ID、维度及编码要求，不把保留旧数据当作旧模型仍可用的证明。
- 可独立执行的词法方法继续工作，通过既有 method / coverage / issues 说明能力与覆盖。
- 来源级增量失败仍按 Q3 只影响变化来源；不适用整体关闭。

依据：[Q6 用户定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980431165)。

## Q7：取消、重试和重启恢复

| 操作或状态 | 已确认行为 |
|---|---|
| 取消 | 请求停止，任务确认停止后显示已取消；保留成功进度，迟到结果不得发布 |
| 重试 | 新建任务记录，核验并复用有效成功工作，只处理未完成或已变化材料 |
| 重启前尚未执行 | 显示需要继续，由用户明确启动 |
| 重启时正在执行 | 按中断失败处理，用户重试，不自动恢复执行 |

恢复前核对来源版本、模型 ID、维度和编码要求，变化材料重新处理。Retry 沿用 predecessor/retry key 和新 successor operation，终态任务不改回 running；Continue 仅用于既有状态机允许的待继续状态，保留原 operation 身份。

请求取消和已取消终态分开，由既有 checkpoint/terminal owner 收敛。启动 reconciliation 不自动 dispatch；普通进度读取或 UI 刷新不修改生命周期。对尚未成功发布的整体重建，重启不恢复旧索引语义查询，完整重建发布后才恢复。已有就绪索引不因重启一律关闭，遵循 Q15。

Public maintenance owner 继续持有执行 winner、生命周期及事件，Retrieval Application 管理私有进度和 rebuild attempt，不另建运行队列。

依据：[Q7 用户定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980467908)。

## Q8：同来源连续变化有界归并

- 短时间内的同来源变化合并处理，只编码最新内容，不逐次执行中间版本。
- 同一来源最多有一个编码工作执行；期间再次变化时不发布过期结果，后续处理最新内容。
- 达到本轮时间或工作量预算后停止，保留进度并显示待更新；用户通过更新索引或状态允许的重试动作恢复，不无限追赶持续变化。
- 合并等待时间、批大小、并发上限通过开发实测确定，不新增公共 search 参数。

归并留在已有 Retrieval Application/维护 owner 内，不新增全库同步队列或独立任务系统。重建期间归并到待发布新索引，不为旧索引编码；版本变化不重置本轮工作预算。停止按既有状态机收敛，不增加通用暂停 interface。

依据：[Q8 用户定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980488008)。

## Q9：空间不足与未完成构建数据保留

- 空间不足时停止构建，保留已落盘的成功进度并显示原因；用户释放空间后重试，复用仍有效的工作。
- 不为腾空间自动删除正式索引、有效构建进度或原始材料。
- 只保留当前一份未完成构建数据，不积累多轮历史，也不按时间自动删除。
- 重试完成后清理临时数据；用户明确丢弃或用另一轮构建替换时，清理原未完成数据。
- 整体重建因空间不足失败时仍保持语义检索不可用，完成重试并整体发布后恢复；可独立执行的词法方法继续工作。

新索引成功发布后的旧数据清理失败及其恢复遵循 Q10。

依据：[Q9 用户定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980522397)。

## Q10：成功发布后的清理失败

- 新索引完整校验并成功发布即达到重建成功界限，恢复语义检索并使用新索引。
- 旧索引或临时数据清理失败不撤销发布，不关闭新索引语义检索。
- 维护任务记录成功，并附清理问题；Home 显示残留数据待清理。
- 用户重试时只重试清理，不重新编码或重建，沿用现有维护入口及生命周期 owner。
- 清理范围仅包含已被替代的旧索引和不再需要的临时数据；重启后保留待清理记录，不自动执行。

Q6 的失败关闭规则适用于发布之前的构建失败；发布之后的清理失败影响空间回收。公开终态和清理工作仍由既有维护 owner 管理，不另建公共接口或独立队列。

依据：[Q10 用户定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980565013)。

## Q11：有效材料与整体完成判断

| 来源情况 | 已确认处理 |
|---|---|
| 本来没有相应内容，例如尚未生成 digest、没有已提取全文或正文为空 | 不要求生成内容；记录覆盖缺口，不阻止发布 |
| 已确认删除、移入回收站或退出纳入范围 | 从本轮计划中移除，排除其片段 |
| 应有内容，但读取失败、文件暂时不可访问、编码失败或响应校验失败 | 保留失败项，阻止整体发布；修复后重试 |

一篇文献没有 digest，可以仅索引已有元数据和全文；已纳入计划的 Markdown 文件读取失败不能当作“没有全文”跳过。构建完成表示本轮应处理的有效材料全部完成，不表示每篇文献都拥有所有类别的内容。

Home 分开展示已完成、无内容或已排除、失败待处理，避免单一百分比掩盖覆盖缺口。此规则细化 Q4 的初建/整体重建完成条件，不改变来源级增量各自发布的单位。

依据：[Q11 用户定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980599523)。

## Q12：索引发布与 Discovery 候选更新分开完成

- 先发布索引、恢复检索，再有界更新候选。来源级增量发布后处理相关候选；初建或整体重建发布后分批处理。
- 候选更新失败不撤销索引发布，不把已成功的重建改为失败；单独显示候选待更新或失败。
- 保留已有 hints 和用户拒绝记录；候选更新仍不能自动加入 Topic 来源。
- 用户恢复候选更新时只处理这部分工作，不重新编码或重建索引。
- 沿用既有维护 owner；重启不自动执行未完成工作，不增加独立队列或公共接口。

索引可检索和候选已更新有各自明确的完成状态；候选处理不作为索引成功发布的前置条件。后续工作沿用既有 admission 和生命周期，不把成功 operation 改回 running。

依据：[Q12 用户定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980620915)。

## Q13：候选连续变化与提交时核验

- 同一 Topic 的连续更新归并处理，使用最新已发布的索引和 Topic 内容；达到预算后保留待更新状态。
- 提交候选前核对相关内容依据；已过期的计算结果不提交，后续只重新处理受影响部分。
- 以提交时的用户意图为准：计算期间新拒绝的文献不能重新出现，已成为 Topic 来源的文献不能再新增为候选。
- 自动更新不覆盖拒绝、恢复或采纳状态；`screened_out` 仍只在证据或匹配依据变化时重新评估。

后台计算开始后用户拒绝某篇文献，迟到结果不能把它重新放回待审候选。提交核验沿用 canonical Topic/Discovery 的既有 owner，不将开始计算时的审阅投影当作当前事实。

依据：[Q13 用户定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980649295)。

## Q14：用户调整索引纳入范围

- 修改纳入的库范围或来源类别时保存为待生效范围，Home 区分当前范围和待生效范围；用户明确启动重建后整体切换。
- 模型、编码要求和来源版本仍兼容的已有向量可以复用，只编码新增或变化材料；整体重建不要求全部重新请求 embedding。
- 新索引排除移出范围的材料，全部完成后将范围与索引一起发布；重建期间遵循 Q5/Q6 的语义检索暂停及恢复规则。
- 已有未完成构建时不悄悄修改其目标。用户选择替换时，先停止原任务，再按新范围构建，复用仍有效的工作。

例如，从库 A 扩展到 A+B，可以复用 A 的有效向量，补建 B 后整体发布。此处调整的是索引纳入范围，查询的硬范围仍按已确认契约执行。

依据：[Q14 用户定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980679290)。

## Q15：漏失通知与外部变化的补查边界

- 用户执行“更新索引”时，在指定的已纳入范围内分页检查当前来源，补充新增材料、更新变化材料、排除退出来源，只重新编码需要变化的部分。
- 启动、打开 Home 和普通搜索不自动扫描全库，也不隐式启动编码。
- 证据搜索仍在同次调用中核验来源；发现已过期片段时不返回旧正文，按既有规则暂停受影响来源并报告缺口。
- 未发现变化不等于确认没有变化。Home 展示最近更新或核验的范围与时间；索引可用不承诺全库实时同步。
- 不因一次重启就关闭全部语义检索；已有重建失败、已知来源变化等状态仍按前述规则处理。

首版由可靠通知负责日常增量，显式更新负责补查，来源核验保证返回证据的有效性。补查只覆盖本次指定范围；检索成功不能证明未召回材料均已更新。

依据：[Q15 用户定案](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5980707213)。

## 已确认的 Discovery 输入

成功入索引的新增/变化文献为相关 Topic 补充候选，Topic 内容成功入索引后更新该 Topic 候选；初建/重建后候选生成是有界后台工作。自动候选只保存 hints，不能自动加入 Topic 来源，既有 triage 与成功 apply 决定采纳。拒绝意图跨重建及模型变化保留，向量不可用时保留已有 hints。

依据：[消费边界对生命周期的输入](https://github.com/leike0813/zotero-agents/issues/82#issuecomment-5977739233)。候选与索引维护的先后、独立完成及失败恢复关系遵循 Q12；连续变化的归并及提交时的审阅状态核验遵循 Q13。

## 生命周期与可见状态汇总

| 触发或状态 | 检索与可见状态 | 恢复或后续工作 |
|---|---|---|
| 尚未初建 | 无正式向量索引；独立词法可用 | 用户明确初建，按 Q11 完成后整体发布 |
| 已有索引，来源变化已确认 | 只暂停受影响来源旧片段，Home 待更新/失败 | 范围内有界增量，来源全部片段校验后一次发布 |
| 已确认来源退出 | 旧来源退出检索 | 从有效计划排除；合并保留项按当前事实处理 |
| 整体重建执行、发布前失败或取消 | 整体语义不可用；独立词法继续 | 保留有效成功工作，用户恢复并完整发布 |
| 新索引成功发布 | 新索引语义可用，模型/编码/范围一起生效 | 清理被替代数据，分批更新 Discovery 候选 |
| 发布后清理失败 | 索引成功、语义可用，附清理问题 | 用户只重试清理 |
| 候选更新失败 | 索引状态保持，候选待更新/失败 | 用户只恢复候选工作，保留已有 hints 和审阅意图 |
| 重启前任务未执行 / 执行中 | 分别待继续 / 中断失败 | 沿用既有 Continue / Retry，不自动 dispatch |
| 未观察到的外部变化或漏失通知 | 不能据此保证实时完整；证据返回仍需来源核验 | 用户显式更新指定范围 |

状态文案不预设新公共枚举。Public maintenance owner 持有任务生命周期，Retrieval Application 持有索引及私有工作进度，Topic/Discovery owner 持有候选与审阅事实。

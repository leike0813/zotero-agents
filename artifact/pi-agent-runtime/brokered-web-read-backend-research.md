# Brokered Web Read backend 一手资料核查

核查日期：2026-08-30。本文为 Wayfinder 研究票 [Research Zotero-compatible Brokered Web Read backends](https://github.com/leike0813/zotero-agents/issues/30) 提供事实与决策底稿，不修改已经由 [Define Trusted Native Execution and Brokered Tools](https://github.com/leike0813/zotero-agents/issues/19) 决定的 Agent-facing schema。

## 结论先行

`web_search` 与 `web_fetch` 是通用 Agent 的基础读取能力。MVP 不以“能够证明网络请求绝对不可能绕过 SSRF 防护”为上线前提；这类证明在应用层普通 HTTP client、DNS、代理和连接复用共同参与时并不现实。项目应兑现一组明确、可测试的防护，并把剩余风险如实归入 Trusted Native Execution 的威胁模型。

MVP 采用一条不要求项目运营服务、也不要求用户先申请专用搜索账户的有序路径：

1. `web_search` 优先复用用户已经配置且支持 hosted search 的模型 provider，由 Tool Gateway adapter 归一结果、预算和错误；
2. 没有可用 provider-native search 时，调用 Exa 官方匿名公共 MCP；
3. 公共 MCP 不可用时，使用一个 credential-free 公共搜索页 adapter 作 best-effort fallback，首个实现从 DuckDuckGo HTML 或 Startpage 中按真实网络验证选择；
4. Brave Search API 与 SearXNG 保留为用户显式配置的 BYOK / self-hosted 选项，不作为默认可用性的前提；
5. `web_fetch` 始终使用 Zotero/Mozilla 原生网络栈。

整条路径只需要 Zotero 内的普通 HTTP adapter，不需要把 Node-only runtime code 引入 Zotero 7 或 Zotero 9，也不要求本项目运营公共 gateway。`web_fetch` 在每一跳执行 URL 解析、DNS 地址分类和响应限制；无法获得连接绑定证明属于已知残余风险，不再单独否决该能力。任意搜索结果 URL 的抓取始终重新进入独立的 `web_fetch` Broker 策略。

Firecrawl 和 Jina Reader 在产品功能上都覆盖 search + fetch，但会引入额外服务、凭据、许可或运维面，并暴露 MVP 不需要的 headers、cookies、browser actions、二进制等能力。原生 fetch 已能完成 MVP，因此不为追求不可验证的“更安全”声明增加远程 fetch gateway；只有动态页面或更强正文抽取成为实际需求时再评估它们。

可用性也属于 MVP 合同：Brokered Web Read 进入有效能力包络后，原生 `web_fetch` 与至少一条 credential-free `web_search` 路径应无需第三方配置即可使用，且不逐次弹窗。Brave key、SearXNG endpoint 与其它专用搜索配置只增强质量或稳定性；全部可用路径失败时返回稳定 `search_unavailable` 及实际失败摘要，不能把需要付费账户或自部署伪装成零配置默认。

### 对本项目的直接含义

1. **没有免费搜索基础设施的“第四条路”。** OpenCode 把运营交给 Exa/Parallel；Pi 放弃内置搜索；OMP 用 best-effort 页面抓取换取零 key。
2. **Brave 与 SearXNG 只能是显式配置选项。** 前者需要用户账户/key，后者需要 endpoint/部署，不能叫默认零配置能力。
3. **若零配置搜索是产品要求，OMP 路线最可复制。** 用多个可失败、可顺序回退的公共页面 adapter，接受限流与维护成本；发布前另行核查站点条款和真实网络可靠性。OpenCode 的匿名 MCP 可作为候选 backend，但不能在没有服务合同的情况下假定它会长期免费替第三方项目承载流量。
4. **已有模型 provider 的 hosted search 值得复用。** 统一包装为本项目的 provider-neutral `web_search` 后端；费用和 quota 仍属于用户账户，不能把模型原生工具直接冒充 Broker contract。
5. **逐次确认不是成熟工具的共同默认。** 三者都允许 Agent 自主进行公共读取，只提供全局或按工具收紧手段；这支持本项目把 `web_search`/`web_fetch` 作为默认可自主调用的 read capability。

## 信任边界与 MVP 风险分层

本票沿用 [Select the cross-platform sandbox architecture](https://github.com/leike0813/zotero-agents/issues/18#issuecomment-5422736114) 的威胁模型：信任 Agent 遵守 Tool Gateway policy，不声称抵抗被攻陷的 Agent；同时把网页、搜索结果、redirect、DNS 回答和工具输出中的指令视为不可信内容。这里需要分开三个对象：

- **Agent 决策可信**：Agent 可以自主决定何时搜索、读取哪个公共 URL，以及如何使用返回的文本，不做逐次确认。
- **网络内容与寻址不可信**：页面内容、链接、redirect 和域名解析不能授予新能力。它们可能包含 prompt injection，也可能把一个看似公共的 URL 引向宿主可见的本地资源。
- **宿主网络资源受保护**：loopback、private、link-local、metadata 和本地 IPC 不属于 Public Web。是否允许读取这些目标由独立 `local-network` grant 决定，不能由 Agent、网页或 `external-egress` 权限自行扩大。

信任 Agent 与保留 Broker 防护并不冲突。Broker 不需要防范 Agent 蓄意突破宿主；它需要阻止不可信页面或寻址过程在 Agent 不知情时把一次普通 Web read 变成宿主网络读取，并确保网页拿不到 Zotero cookie、凭据或请求正文。

### 默认硬拒绝

Agent 只看到：

- `web_search { query }`
- `web_fetch { url }`

输出只允许有界的搜索 title/URL/snippet，或 final URL/content type/Markdown/plain text。HTML、plain text 和 JSON 可读；其它 MIME 返回 `unsupported_content_type`。以下能力对 Public Web 读取始终拒绝，不能由 Agent 参数放开：

- 非 HTTP(S) scheme、URL embedded credentials、GET 之外的 method、request body 和用户自定义 header；
- Zotero cookie jar、HTTP auth、client certificate、provider key 或其它宿主凭据；
- 二进制下载、文件物化、页面脚本执行、插件 DOM 注入或 Shell fallback；
- 超出 redirect、解压后字节、MIME、总时长、空闲时长和单 turn 调用预算的响应。

Public Web 默认还拒绝 literal 或当前 DNS 结果中的 loopback、private、link-local、multicast、unspecified、documentation 和 metadata/special-purpose 地址；任一 A/AAAA 落入拒绝范围即拒绝整次请求。已知 cloud metadata endpoint（至少包括 `169.254.169.254` 与 `metadata.google.internal`）始终拒绝。每次 redirect 都关闭自动跟随，重新做 URL、DNS 和地址分类。OWASP 对“任意外部 URL”场景同样建议只允许 HTTP(S)、检查全部 A/AAAA、分类非公共地址并逐跳验证 redirect，同时明确 DNS pinning/TOCTOU 是应用层校验面对的现实难点。[OWASP SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)、[OWASP SSRF Top 10](https://owasp.org/Top10/2021/A10_2021-Server-Side_Request_Forgery_%28SSRF%29/)、[AWS IMDS](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-service.html)、[Google Cloud metadata](https://cloud.google.com/compute/docs/metadata/querying-metadata)

### 可由用户配置或授权放开

- Public Web 可以配置 domain allowlist/blocklist、调用预算，以及确有需要的公开非标准端口；这些配置只能缩小或有界扩展目标，不能注入 header、cookie 或请求正文。
- 普通私网、本机或组织内部站点只能通过既有独立 `local-network` capability 放开。Gateway 从解析结果推导 `local-network` effect，暂停原调用并走既有增量授权路径；授权后仍使用同一个只读、匿名、有界 `web_fetch`，不新增 Broker 专用 allowlist 体系，也不降级为通用 HTTP。cloud metadata endpoint 即使有 Local Network grant 也保持硬拒绝。
- 用户可以选择保留 Firefox/Zotero 的系统代理、DoH 和企业网络配置。Mozilla channel 明确区分 origin DNS 与 proxy DNS；此时 receipt/诊断应标明 `proxy-mediated` 或等价事实，不能宣称本地 preflight DNS 就是代理最终连接地址。宿主网络配置属于受信控制面，而不是网页内容提供的参数。[Mozilla proxy DNS strategy](https://searchfox.org/firefox-main/source/netwerk/protocol/http/nsIHttpChannelInternal.idl#551-583)

### 接受并降低的残余风险

应用层 preflight 与实际 connect 之间仍可能发生 DNS rebinding/TOCTOU；连接复用、Alt-Svc、代理端 DNS 或平台内部重新解析也可能使“预查地址”与“实际 peer”不同。Mozilla 的内部 channel 暴露实际 `remoteAddress`，但接口明确说明端点尚未确定或 HTTP activity observer 未启用时可能不可用，因此它适合作为可用时的二次检查与审计证据，不适合作为能力存在的绝对前提。[`nsIHttpChannelInternal.remoteAddress`](https://searchfox.org/firefox-main/source/netwerk/protocol/http/nsIHttpChannelInternal.idl#330-345)

MVP 接受这部分残余风险，理由是影响已被窄化：请求固定为匿名 GET、无 body/secret、自行处理 redirect、只把有界文本返回给受信 Agent；若可取得 actual remote address 且发现非公共地址，应立即 abort、丢弃响应并记录 `network_denied`。这不能倒推为“请求从未触达该地址”，所以文档和 receipt 只承诺 **best-effort SSRF mitigation**，不宣称 Strong network isolation。

网页内容仍可能诱导 Agent 发起后续调用或污染结论。处理方式是保留来源 URL、把页面标记为不可信 tool output、限制调用与响应、让 Agent 引用和交叉核验；不尝试用 URL 安全检查解决 prompt injection。

### 统一执行合同

每次执行必须满足：

- 默认只访问公共 HTTP(S)，独立 Local Network grant 可以有界放开明确目标；
- DNS 后尽力拒绝 loopback、private、link-local 和其它非公共地址；
- 每次 redirect 都重新做 URL、DNS 和地址分类；
- 不携带 Zotero cookie jar、用户凭据或任意认证头；
- 对 redirect 次数、响应 MIME、解压后字节数、总时长和空闲时长设硬上限；
- 传播 `AbortSignal`，并把 validation、network、timeout、cancel、unsupported content、resource limit 和 unavailable 分成稳定错误；
- provider key 只能是 Broker 持有、绑定到固定 provider origin 的 connection secret，不能成为 Agent 参数，也不能转发给目标网页。

这些是项目 Tool Gateway/Broker 的职责。下文的 “backend 有某能力” 只表示它可被利用；安全声明必须与项目实际能测试和观察的边界一致。

## Zotero/Mozilla fetch 的具体可行性

### 能直接复用的能力

Zotero 7 与 9 的 `Zotero.HTTP.request()` 都已有以下 primitive：

- 关闭自动 redirect，并取得 redirect status/Location；
- 指定 response type；
- timeout；
- cancel callback；
- offline detection。

Zotero 9 还明确增加 `anon`/`userContextId` 行为说明。对本工具只能用匿名路径，不能创建 cookie context。标准 `fetch()`/`Response.body` 可用于逐 chunk 计数与及时 abort，`DOMParser` 可把允许的 HTML 解析成不挂入可见 DOM 的 document，再生成纯文本。解析后的 untrusted DOM 不能插入 UI；MDN 明确把 `parseFromString()` 视为 injection sink。

### best-effort SSRF 边界

`followRedirects: false` 和 `nsIDNSService.asyncResolve()` 足以实施 MVP 的逐跳 preflight，但不能组成原子的 check-and-connect。以下事实应进入 receipt、诊断和测试说明，而不是成为无限期上线门禁：

1. 连接使用的地址是否就是刚刚检查过的地址；
2. A/AAAA 多地址是否全部检查，而不是只检查首个；
3. redirect 的 Location 是否在发起下一跳前重新走完整校验；
4. proxy、DNS-over-HTTPS、系统 DNS cache 或 re-resolution 是否造成 policy/connection 不一致；
5. 在收到 headers/body 前能否确认实际 remote address 仍为公共地址。

实现应优先检查所有 preflight A/AAAA；若 channel 暴露实际 `remoteAddress`，在接收 body 前后复核并在发现非公共地址时丢弃响应。代理代为解析、接口不可用或竞态无法消除时，请求仍可在 Public Web grant 下执行，但必须如实标为 best-effort。用户需要更强隔离时，应通过部署层网络策略或未来 Strong Executor 提供；普通插件 fetch 不冒充该能力。

### 与成熟 Agent 工具的真实实践比较

成熟产品也把 Web 能力作为有界工具提供给 Agent，而不是等待“绝对安全”证明：

- OpenAI Agents SDK 直接把 hosted `web_search` 列为 Agent tool，并提供 `allowedDomains` 等过滤选项。[OpenAI Agents SDK tools](https://openai.github.io/openai-agents-js/guides/tools/#hosted-tools)
- Anthropic 的 hosted `web_fetch` 支持 domain allow/block、`max_uses`、内容上限和稳定错误；它拒绝 private addresses，并限制自动 fetch 的 URL 必须已出现在用户消息、搜索结果或先前工具结果中。其文档同时警告不可信输入与敏感数据并存时存在外泄风险，没有把该工具描述为绝对隔离。[Anthropic Web fetch](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool#tool-definition)、[URL validation 与 errors](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool#url-validation)
- GitHub Copilot cloud agent 默认以 firewall 和 allowlist 限制互联网访问，也允许管理员配置甚至关闭 firewall；官方明确承认复杂攻击可能绕过，保护常见场景但不是完整安全方案。[GitHub Copilot firewall](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-the-firewall#limitations)

由这些一手资料可作出的推论是：可用的 Agent Web 工具采用域过滤、来源与预算限制、结构化拒绝、告知和审计来降低风险，同时承认实施边界。Zotero MVP 应采用同一路径。Anthropic 的“URL 必须先出现在上下文”可作为未来可选的严格档位或审计信号；本项目既已信任 Agent，默认不禁止 Agent 构造合法公共 URL，以免削弱文档定位、API discovery 等核心用法。

## 必须由 Tool Gateway/Broker 实现的统一 adapter

无论请求最终由 provider-native search、Exa MCP、公共页面 adapter、Brave、SearXNG 或将来的 backend 执行，下面逻辑只有一份 SSOT：

1. **输入**：保持原 schema；内部限制 query/URL 长度，URL 只接受 HTTP(S) 且不得包含 userinfo。Agent 可以构造公共 URL，不要求它先出现在 transcript 或搜索结果中。
2. **provider 配置**：backend kind、base URL、provider key、预算和 timeout 都是 host config，不进入 tool schema。
3. **凭据**：只向固定 provider origin 注入该 provider 的 key；目标页面永远使用 anonymous/credentials-omit，无 Cookie、Authorization、Proxy-Authorization、client certificate 或用户 headers。
4. **搜索结果**：把 provider-specific JSON 归一为有界 title/URL/snippet；丢弃 provider 控制字段，结果 URL 不自动抓取。
5. **fetch preflight**：用平台 URL parser 规范化 URL；解析全部 A/AAAA，并按 [IANA IPv4 special-purpose registry](https://www.iana.org/assignments/iana-ipv4-special-registry) 与 [IPv6 special-purpose registry](https://www.iana.org/assignments/iana-ipv6-special-registry) 分类，不能靠字符串正则处理 IP literal。metadata 永久拒绝；其它非全局可达地址默认拒绝，只有既有 Local Network grant 可放开。公开非标准端口按 host policy 配置。
6. **redirect loop**：关闭自动 redirect；限制跳数；每一跳重新执行 URL、DNS 与地址检查。任何一跳需要 Local Network grant 时暂停，不继承上一跳的 Public Web 判断。
7. **body gate**：先检查 status 与 MIME，再流式读取；按解压后实际 byte 计数；只接受 HTML、plain text、JSON，超限立即 abort；不落盘、不返回 base64。
8. **提取**：JSON 解析后有界序列化；HTML 在隔离 document 中做确定性 text extraction。Markdown 只是输出表示，不能执行页面脚本或读取 Zotero DOM。
9. **生命周期与网络证据**：把 caller `AbortSignal`、总 timeout、idle timeout 传到底层；区分 cancel 与 timeout。可用时复核 channel `remoteAddress`；记录 direct/proxy-mediated、preflight/peer 是否可观测和策略结论，不把缺失证据写成 enforcement success。远程服务没有 provider-side cancel 证明时，诊断标成 caller-aborted，而不是 remote-cancel-confirmed。
10. **失败与 fallback**：未配置、无凭据、quota/rate、DNS policy、redirect policy、unsupported MIME、response too large、timeout、cancel 和普通 network failure 使用既定稳定 metadata。`web_search` 只可沿固定、可观察的无副作用 provider chain 前进；不得改走 Shell 或任意 HTTP，cancel 后不得继续 fallback。审计遵循既有 persistence-safe projection，不持久化页面正文、完整敏感 URL 或原始 header。

## 组合结论

| 顺序 | `web_search` | `web_fetch` | 选择理由 | 明确代价 |
| --- | --- | --- | --- | --- |
| 1 | 已配置模型 provider 的 hosted search | Zotero/Mozilla native + Broker guard | 复用用户已有账户、OAuth/API key 与 quota，不增加搜索专用配置 | provider 覆盖与费用不一致；必须由项目 adapter 归一，不能直接暴露 provider tool |
| 2 | Exa 匿名公共 MCP | 同上 | 官方远程 MCP 面向通用 client，零 key、零自部署；OpenCode 已采用同一路径 | 没有项目可依赖的长期免费或 SLA 合同，失败时必须继续降级 |
| 3 | 一个公共搜索页 adapter | 同上 | 零 key、零运营；只需维护一个最小 parser | best-effort，会受 CAPTCHA、限流、页面改版与站点条款影响 |
| 显式选项 | Brave BYOK / SearXNG self-hosted | 同上 | 用户需要更稳定或可控的搜索时主动配置 | Brave 需要账户/key，SearXNG 需要 endpoint 与运维，均不承担默认可用性 |

因此，MVP 保持两个 operation、共享一层 Broker policy：搜索使用上述最小有序链，抓取只使用 Zotero/Mozilla native。项目不运营服务，不要求用户为基础搜索先申请专用账户，也不复制 OMP 的完整多 provider/多 scraper 体系；一个匿名 MCP 和一个页面 adapter 足以覆盖零配置 fallback。远程 fetch backend 不是原生 fetch 的安全前提。

## 排除项

- **Bing Search API**：Microsoft 已于 2025-08-11 完全退役该产品；Grounding with Bing Search 属于 Azure AI Agent/provider-native surface，不能作为通用 Tool Gateway search endpoint 的等价替代。[Microsoft retirement notice](https://learn.microsoft.com/en-us/lifecycle/announcements/bing-search-api-retirement)
- **Google Custom Search JSON API**：已对新客户关闭，现有客户必须在 2027-01-01 前迁移；不适合作为新 MVP 的默认依赖。[Google official notice](https://developers.google.com/custom-search/v1/overview)
- **模型生成过程自行调用、未经过 Tool Gateway adapter 的 search**：不能冒充 `web_search`。由 Tool Gateway 持有 adapter、接收相同 `{ query }`、返回 provider-neutral result 并应用统一 budget/error/audit 的 provider-native search 属于选定实现路径。
- **任意 HTTP、Cookie/认证 header、二进制、Shell**：均已被上游决策排除，不因某个 backend 支持这些功能而重新进入范围。

## 上线前最小证据门禁

本票能决定 substrate，不能替实现签发 Strong network isolation 证明。实现阶段需要验证项目实际承诺的行为：

- Zotero 7 与 Zotero 9 各一次 `web_search`/`web_fetch` happy path；
- literal 与 DNS-resolved loopback/private/link-local 拒绝；
- 已知 cloud metadata address/hostname 即使存在 Local Network grant 仍拒绝；
- public URL redirect 到 private address 拒绝；
- multi-A/AAAA 中任一非公共地址导致拒绝；
- 对 private/loopback 的明确 Local Network grant 能放行原 `web_fetch`，未授权时返回既有 permission/policy 结果；
- redirect 次数、HTML/text/JSON MIME、解压后 size、总/idle timeout 和 cancellation 边界；
- anonymous request 不携带 Zotero cookie jar 或用户 Authorization；
- Agent 构造、但未预先出现在 transcript/search result 的公共 URL 可以读取；
- direct 与 proxy-mediated 路径如实报告可观测的 DNS/peer 证据；`remoteAddress` 不可用不冒充 enforced，也不单独禁用 Public Web fetch；
- 已配置 provider-native search 的归一结果、费用/quota 错误与 credential 隔离；
- Exa 匿名 MCP 的零 key happy path、timeout/rate/unavailable 降级；
- 单个公共搜索页 adapter 的 parser fixture、challenge/改版检测与稳定失败；
- 固定 provider chain 的顺序、cancel 终止和 all-failed `search_unavailable` 摘要；
- Brave/SearXNG 未配置时不影响零配置链，显式选择时返回稳定配置错误；
- backend result normalization 不改变 Agent-facing schema，且 provider-specific 字段不泄漏到模型合同。

验收结论应明确写成“已通过列出的 best-effort SSRF 防护”，不得写成“DNS rebinding 不可能”或“实际 socket 与 preflight DNS 绝对一致”。

搜索“质量”不能用供应商自述代替。应使用一小组与 Zotero 工作流相关、固定期望域/文献类型的查询比较 URL relevance、重复率、语言覆盖和空结果；该 eval 只决定默认 backend，不改变工具 schema。

## C09 revalidation (2026-09-04)

### Exa anonymous public MCP

**推荐保留 Exa，且用 Zotero/Mozilla 原生 HTTP 实现最小 client；不需要 MCP SDK。** 官方匿名入口是 [`https://mcp.exa.ai/mcp`](https://mcp.exa.ai/mcp)，transport 为 Streamable HTTP；其 HTTP 响应可为 SSE，SSE `data:` 承载 JSON-RPC 响应，而不是另一个常驻 WebSocket/SSE client。[Exa MCP reference](https://exa.ai/docs/reference/exa-mcp)、[MCP Streamable HTTP (2025-03-26)](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports)

本次对该入口的无凭据实测（2026-09-04，`Accept: application/json, text/event-stream`）得到 `200 text/event-stream` 和 `Mcp-Session-Id`：`initialize` 协商 `2025-03-26`，随后 `notifications/initialized` 返回 `202` 空体；携带 session 与 `MCP-Protocol-Version: 2025-03-26` 的 `tools/list`、`tools/call` 返回单条最终 SSE message。最小序列因此是：

1. `POST initialize`，JSON-RPC `id`，`protocolVersion: "2025-03-26"`、空 `capabilities` 和 `clientInfo`；保存 `Mcp-Session-Id`。
2. `POST notifications/initialized`，携带该 session。
3. `POST tools/list`，再按返回名称 `POST tools/call`；所有请求带 session、protocol-version、JSON body 和上述 Accept 值。

匿名默认暴露 `web_search_exa`、`web_fetch_exa`；`?tools=` 可额外启用工具。匿名额度有限，`x-api-key` 可提高额度；官方也列出 Bearer、query key 与 OAuth，但本项目若日后配置 key，只应注入 header，不能把 key 放入 URL。[Exa MCP reference](https://exa.ai/docs/reference/exa-mcp)、[Exa MCP server source](https://github.com/exa-labs/exa-mcp-server)

超时由 client 自己计时；超时或调用方 abort 后，另发 JSON-RPC `notifications/cancelled`，再停止读取。关闭本地 SSE 读取不等于远端取消；协议允许服务端忽略已完成或未知 request id。本次只验证了已完成请求的 cancellation 得到 `202`，没有把公共服务的在途搜索或额度打满来伪造保证。未知工具在实测中仍是 `200` SSE，错误在 MCP `result.isError`/文本（`-32602`）中；免费额度耗尽官方说明为 `429`，但没有可依赖的 `Retry-After` 或远端取消完成契约。故 adapter 必须分别归一 transport/JSON-RPC/tool error、429、local timeout 与 caller-aborted。[MCP cancellation](https://modelcontextprotocol.io/specification/2025-03-26/basic/utilities/cancellation)、[MCP lifecycle](https://modelcontextprotocol.io/specification/2025-03-26/basic/lifecycle)、[Exa rate-limit troubleshooting](https://exa.ai/docs/reference/exa-mcp)

这只要求原生请求的 POST/header/text-body 能力，加一个很小的 SSE `event:`/`data:` 分帧器；常规调用可缓冲单个最终 event 后解析。SDK 仅节省封装代码，既非协议要求，也不是 Zotero 7/9 的生产依赖理由。残余不确定性是匿名额度、服务端版本与额外工具集合没有 SLA；它必须保持为可失败的第二级 fallback。

### Credential-free page-search fallback

**最小候选只能暂定 DuckDuckGo HTML，且当前不应作为自动上线的可用 backend。** 本次无 Cookie、带常见 Firefox UA 的直接请求中：

- `GET https://html.duckduckgo.com/html/?q=Zotero` 为 `200 text/html`，但正文不是结果列表：有 `form#challenge-form`、`[data-testid="anomaly-modal"]` 和人工图片挑战文字；`POST https://html.duckduckgo.com/html/` 也为 `202` challenge。因此结果链接/URL/snippet 的正常 HTML 结构在当前网络条件下不可验证，parser 必须把这些 challenge markers 或缺少结果节点视为稳定 `search_unavailable`，绝不能把 HTTP 200 当成功。[live GET endpoint](https://html.duckduckgo.com/html/?q=Zotero)
- DuckDuckGo 的 [`robots.txt`](https://duckduckgo.com/robots.txt) 对 `/html` 和 `/lite` 明确 `Disallow`。robots 不是许可条款，但这是明确的反爬信号；通用 [Terms](https://duckduckgo.com/terms) 要求按服务授权使用并保留暂停访问权，未给出该 HTML surface 的自动查询 API 合同。
- Startpage 当前官方给浏览器 search-string 的 GET 是 [`https://www.startpage.com/sp/search?query=%s`](https://support.startpage.com/hc/en-us/articles/4520913488148-Search-strings)；官方还说明默认 POST 到 `/sp/search`，旧式 GET 示例为 `/do/dsearch?q=…&cat=web`。[Startpage GET/POST](https://support.startpage.com/hc/en-us/articles/5265503371412-POST-versus-GET) 但本次对前者 GET 和 `/sp/search` POST 都获得 `200 text/html` challenge：有 `spchal-cookie-verification`/`sp_pow` cookies，正文含 `anubis_challenge` 的 proof-of-work JSON 与脚本。这既不是无 JS/cookie 路径，也没有可供解析的正常结果结构。
- Startpage 明说会阻止快速 automated searches、把 CAPTCHA/security-check cookie 用于反滥用，并把无 UA 和 scraper 作为 bot 信号；其 CAPTCHA 是面向自动程序的防护，而不是可重试的空结果。[privacy policy](https://safe.startpage.com/en/privacy-policy/)、[user-agent policy](https://support.startpage.com/hc/en-us/articles/5012065088020-Startpage-and-user-agents)、[CAPTCHA support](https://support.startpage.com/hc/en-us/articles/4521350590996-Why-am-I-receiving-a-CAPTCHA-verification-page)

DuckDuckGo 相比 Startpage 没有当前观测到的 JS proof-of-work，故若产品仍坚持保留一个极小的页面 adapter，它是唯一可做**显式、低频、可随时移除的候选**：只 GET、只解析正常 server-rendered 结果，命中 challenge/selector drift/403/429/5xx 即立即停止并返回稳定 unavailable，绝不解挑战、保留 cookie、伪造浏览器信号或重试绕过。然而本次实测已被挑战且 robots 排除了该 surface；在取得站点授权或看到稳定、合规的自动访问证据前，默认实现应跳过两者，走 Exa 失败后的 `search_unavailable`，而不是把公共结果页包装成可靠的 credential-free API。

## C09 DeepSeek search feasibility (2026-09-04)

**结论：DeepSeek 现在有稳定的官方 hosted web search，但它是 `/responses` 内的 server-side tool，不能列为 C09 的 raw `web_search` adapter。** 本次在官方 API reference / Responses guide 中没有发现独立的 `/search` endpoint；官方定义的是 `POST https://api.deepseek.com/responses`，模型为 `deepseek-v4-flash`、`deepseek-v4-pro` 或 `deepseek-v4-flash-vision-exp`，以 Bearer API key 认证。`tools` 可含 `{ "type": "web_search" }` 或 `{ "type": "web_search_2025_08_26" }`，并由服务端执行；`tool_choice: { "type": "web_search" }`（或版本化名称）会强制一次 web search，缺少相应 tool 会返回 400。[Responses endpoint/schema](https://api-docs.deepseek.com/api/create-response/)、[Responses guide compatibility table](https://api-docs.deepseek.com/guides/responses_api/)

它仍是模型生成请求而非“一条 query 对一张 SERP”：输入是 string 或消息 item 加可选 `instructions`，服务端可进行 search、open_page、find_in_page，并有最多十轮的 server-side auto-continuation；`search_context_size`、`user_location`、`max_tool_calls` 均被官方标为 ignored。同步 response 或 SSE 终态会有 `message`/`reasoning`/`web_search_call` 和 token usage；SSE 有 web-search in-progress/searching/completed 状态。官方契约只把 `web_search_call.action` 定义为动作描述，未定义可供调用方消费的 ranked `results[]`、URL/title/snippet 或 citation contract；因此可保留 grounded answer、model、usage、action status，却不能凭空声称 DeepSeek 返回可审计 sources/citations。[工具、轮次和不支持参数](https://api-docs.deepseek.com/guides/responses_api/)、[输出 item 与 action schema](https://api-docs.deepseek.com/api/create-response/)

普通 Chat Completions 的 `tools` 与此不同：官方只支持 `type: "function"`，`tool_choice` 至多强制模型**生成**某个函数的 JSON arguments；文档明确要求调用方验证 arguments、执行函数、再回传 tool output。把用户定义的 function 命名为 `web_search`，或使用 OMP 的 “DeepSeek-style in-band tool calls”，都不能证明 DeepSeek 自己执行了网络搜索，也不能替代上述 Responses server tool。[Chat Completions tool schema](https://api-docs.deepseek.com/api/create-chat-completion/)、[官方 Tool Calls guide](https://api-docs.deepseek.com/guides/tool_calls/)、[OMP 的 in-band format setting](https://github.com/can1357/oh-my-pi/blob/b8ce33a58911c26bed1d84f0db9a5e2e727c49a2/packages/coding-agent/src/config/settings-schema.ts#L2738-L2785)

费用/配额仍是该模型请求的账户成本：官方只发布 token pricing，并在 DeepSeek 的 Claude Code integration 中说明 web search 还会产生用于总结检索内容的额外模型 token；未发布独立 search-call 价目或免费额度合同。`v4-pro`/`v4-flash` 账户级并发上限分别为 500/2500，超限为 429；标准错误还包括 401、402、422、500、503。Responses 是 stateless、`background` 不支持，官方没有列出 response/web-search cancel endpoint；所以 Zotero adapter 只能以本地 HTTP deadline/abort 停止读取，不能承诺远端 search 已停止，并须处理 SSE keep-alive/comments 与 `response.failed`/`incomplete`。[pricing](https://api-docs.deepseek.com/quick_start/pricing/)、[web-search additional-token statement](https://api-docs.deepseek.com/quick_start/agent_integrations/claude_code/)、[rate limit](https://api-docs.deepseek.com/quick_start/rate_limit/)、[errors](https://api-docs.deepseek.com/quick_start/error_codes/)

OMP 18.0.11 **没有** DeepSeek `SearchProviderId`、provider factory 或 `src/web/search/providers/deepseek.ts`；它的 Web Search order/registry 只列 Perplexity、Gemini、Anthropic、Codex、xAI、Z.AI、Exa 等。DeepSeek 在 OMP catalog 是普通 `openai-completions` model（`https://api.deepseek.com`）；该 transport 只将本地/客户端 functions 放入 `params.tools`，并解析 Chat Completions endpoint，未调用 DeepSeek `/responses` server-side web search 或实现其 events/citations/cancel。故不能因“OpenAI-compatible”或 in-band tool-call formatting 名称而误称 OMP 已实现 DeepSeek native web-search provider。[OMP web provider options](https://github.com/can1357/oh-my-pi/blob/b8ce33a58911c26bed1d84f0db9a5e2e727c49a2/packages/coding-agent/src/web/search/types.ts#L7-L113)、[lazy provider registry](https://github.com/can1357/oh-my-pi/blob/b8ce33a58911c26bed1d84f0db9a5e2e727c49a2/packages/coding-agent/src/web/search/provider.ts#L14-L105)、[OMP DeepSeek catalog entry](https://github.com/can1357/oh-my-pi/blob/b8ce33a58911c26bed1d84f0db9a5e2e727c49a2/packages/catalog/src/models.json#L57728-L57760)、[OMP OpenAI Completions tool mapping](https://github.com/can1357/oh-my-pi/blob/b8ce33a58911c26bed1d84f0db9a5e2e727c49a2/packages/ai/src/providers/openai-completions.ts#L1708-L1842)

故 C09 不应接入 consumer Web endpoint、网页抓取，也不应伪造 function tool。若产品决定增加 DeepSeek，则最小实现是**显式 BYOK 的 `resultKind: "grounded_answer"` adapter**：Gateway 固定 origin `api.deepseek.com`，发送 `/responses` + server `web_search` + 强制 tool choice，解析 SSE/最终 response 后只输出 answer、`webSearchPerformed`/actions、model、usage 和 provider request id；当没有官方 citation/source 字段时，`sources` 必须为空或 omitted。它只需要 Zotero 原生 HTTPS POST/SSE parser，不引入 SDK；仍须由 Gateway 持有 key、时限、预算、redaction、审计与 failure mapping。它不进入 raw `web_search {query} -> sources[]` MVP，除非 DeepSeek 后续发布可稳定消费的 source/citation result contract。

## C09 official MCP client/runtime revalidation (2026-09-04)

**结论：Zotero 的 MCP Tool Source MVP 应自行实现小型、仅 remote Streamable HTTP 的 JSON-RPC adapter；不引入官方 TypeScript client runtime。** 当前稳定协议 revision 是 `2026-07-28`，其 core 已是无 session、无 `initialize` 的按请求模型：每个请求携带 protocol version、client identity/capabilities 的 `_meta`，可选 `server/discover` 取能力；Streamable HTTP POST 还须将 body method/name 复写为 `Mcp-Method` / `Mcp-Name` headers。它取代 2025-11-25 及以前的 lifecycle，后者仍要 `initialize {protocolVersion, capabilities, clientInfo}` → server version/capabilities/info → `notifications/initialized`，随后 HTTP 请求携带 negotiated `MCP-Protocol-Version`，并只使用双方已协商 capability。客户端需要同时实现 modern 和 legacy 的版本选择/拒绝路径，不能把某一个 `initialize` example 当成全体 MCP。[2026-07-28 release/modern lifecycle](https://blog.modelcontextprotocol.io/posts/2026-07-28/)、[legacy lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)、[2025 schema](https://modelcontextprotocol.io/specification/2025-11-25/schema)

标准 transport 只有 newline-delimited JSON-RPC 的 **stdio** 和 **Streamable HTTP**；前者要求 client launch/terminate 子进程，因而不属于 Zotero browser-like runtime。Streamable HTTP 是 POST JSON-RPC，response 可以是 JSON 或有限/长 SSE；legacy `HTTP+SSE` 仍有 SDK compatibility transport，但在 2026 revision 已正式 deprecated，不能作为新 client 默认。对于 legacy Streamable HTTP，server 可在 initialize response 下发 `Mcp-Session-Id`，client 后续必须回送，404 须重建 session，闲置 client SHOULD 以携带该 header 的 DELETE 终止（405 表示 server 不允许）；SSE `Last-Event-ID`/reconnect 也只是 2025-era。2026-07-28 移除了 session/header、GET/DELETE session 操作和 stream resumption：list/resource cache hints 与 `subscriptions/listen` 替代 unsolicited listChanged；中止 modern in-flight request 的信号是关闭该 request 的 SSE response，legacy/stdio 才发 `notifications/cancelled`。legacy cancellation 仍是 best-effort：receiver 可忽略未知、已完成或不可取消的 id；task call 应使用 `tasks/cancel` 而非 cancellation notification。[standard transports and legacy session/DELETE](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)、[cancellation](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation)、[official TS SDK version behavior](https://ts.sdk.modelcontextprotocol.io/v2/protocol-versions)、[SDK cancellation migration](https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28)

官方 TypeScript 发布线目前明确 split：旧的一体包 [`@modelcontextprotocol/sdk@1.30.0`](https://registry.npmjs.org/@modelcontextprotocol/sdk/-/sdk-1.30.0.tgz) 仍为 Node `>=18`、含 client/server、HTTP/SSE/stdio 与一大组 server framework dependencies；新线是 [`@modelcontextprotocol/core@2.0.0`](https://registry.npmjs.org/@modelcontextprotocol/core/-/core-2.0.0.tgz)（公开 Zod schemas，Node `>=20`）和 [`@modelcontextprotocol/client@2.0.0`](https://registry.npmjs.org/@modelcontextprotocol/client/-/client-2.0.0.tgz)（同样 Node `>=20`）。tarball import graph 的细节很重要：v2 root HTTP client 静态用 `eventsource`、`eventsource-parser/stream`、`pkce-challenge`，可动态 import `jose`，但**没有** `node:` import；它确有 `browser` condition，若 bundler 正确选择该 condition，就选 CF-worker validator shim。相反 `@modelcontextprotocol/client/stdio` 才静态 import `node:process`/`node:stream`，不可进入 Zotero bundle；不识别 browser condition 的 resolver 会落到 Node/AJV shim。core 的 public entry 只依赖 Zod、tarball dist 无 Node import，`./internal` 则是 SDK internal API，不能依赖。整个发布包仍很重（v2 client 解包 dist JS 约 1.76 MB / package 6.65 MB；v2 core 213 KB / 1.33 MB；v1 SDK dist JS 约 1.59 MB / 6.08 MB），并且 manifest 的 Node engine 不是 Zotero 兼容声明。结论因此是：**技术上可对 v2 root HTTP client 做一次受控 browser-condition bundle audit，不能使用 stdio；但在未证明 Zotero 7/9 的 resolver、EventSource/fetch stream、OAuth callback 和 tree-shaking 组合前，不把它作为产品 runtime 依赖。** 对 C09 仅 tools 的窄范围，自有 adapter 更小、更可审计；官方 SDK 的 browser shim 不是充分的兼容保证。[v2 client immutable manifest](https://registry.npmjs.org/@modelcontextprotocol/client/2.0.0)、[core manifest](https://registry.npmjs.org/@modelcontextprotocol/core/2.0.0)、[v2 client connection docs](https://ts.sdk.modelcontextprotocol.io/v2/clients/connect)、[v1 published manifest](https://registry.npmjs.org/@modelcontextprotocol/sdk/1.30.0)

可复用的范围应限于 `@modelcontextprotocol/core` 的 JSON schemas/常量作为**开发时参照或可选 schema source**；它仍须先经 Zotero build/runtime compatibility audit，不能作为默认 runtime dependency。MVP 自有 adapter 只实现：modern `server/discover`（若要 discovery）、`tools/list`、`tools/call`、JSON-RPC error/result、请求 deadline/Abort、响应 SSE framing、modern `_meta` + headers，及为兼容真实 2025 servers 的窄 legacy initialize/session/`notifications/initialized`。仅 remote HTTPS origin，拒绝 stdio、custom transport、legacy SSE（除非某个已批准 server 的测试证明必须）、SSE reconnection/resumption、task、OAuth 和 server→client request。这样保持在 Zotero 原生 HTTP 能力内，同时保留协议版本/错误的明确升级点。

“完整 MCP”远超过 tool source。对一个只消费远端 tools 的 client，server capability `tools`、`tools/list`（含分页）、`tools/call`、tool input/output schema 和可选 list-changed/cache 语义才是必需面；`resources`、`prompts`、`logging` 只是 server 提供的其它输出面，均不必为工具发现调用。相反，legacy `roots/list` 暴露本机 `file:` workspace、`sampling/createMessage` 要插件代 server 调用模型且可能允许 server 驱动模型 tools、`elicitation/create` 要服务端向用户索取表单/浏览器交互；tasks 又加入 durable work、poll/cancel/result，2026 新 model 以 MRTR 的 `input_required` 重试替代这些 held-open server-to-client requests。现代 spec 还已 deprecate roots/sampling/logging；新实现不应广告它们。它们每一个都会扩大 host filesystem、model credential/billing、用户 consent、URL navigation 或 durable lifecycle 的攻击面，故 MVP capability 必须 fail-closed 为 `{}`，并对 server 发来的未协商 request 回 JSON-RPC error，而不是忽略后继续。[client capability schema](https://modelcontextprotocol.io/specification/2025-11-25/schema)、[elicitation security](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation)、[tasks scope](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks)、[2026 MRTR/deprecations](https://blog.modelcontextprotocol.io/posts/2026-07-28/)

`annotations`（`readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint`）和 description/effect metadata **不是授权或强制机制**。规范明说 annotations 都只是 hints、来自不可信 server 时 client MUST 当作不可信；即使默认值悲观，也不能以 `readOnlyHint:true` 自动授予 Zotero/网络/写入权限。对任意用户配置 server，Gateway 应以 server origin/identity + 每个允许的 namespaced tool + 传入 arguments 自己判 effect、预算、approval、secret egress，并显示 input；缺 schema、冲突名称、未知 capability、无效/过大 result 或无法在政策中分类的 tool 一律拒绝。server `name` 也不保证唯一，聚合工具要采用配置实例的稳定 identifier prefix，而不能依 name 认定身份。[tool annotations schema](https://modelcontextprotocol.io/specification/2025-06-18/schema)、[tools trust/collision guidance](https://modelcontextprotocol.io/specification/draft/server/tools)

受保护 remote server 不能以“Bearer header 能连上”替代 OAuth client。MCP OAuth 要 client 用 RFC 9728 Protected Resource Metadata 发现 authorization server（优先 401 `WWW-Authenticate: resource_metadata`，否则 endpoint-path/root well-known），并支持 RFC 8414 与 OIDC discovery；authorization/token request 都须 RFC 8707 `resource`，PKCE（尽可能 S256）且客户端必须从 AS metadata 验证 PKCE，验证 RFC 9207 authorization response `iss`，并把 client registration、access/rotated refresh token 按 authorization-server issuer 隔离。2026 方向已是 Client ID Metadata Document；DCR 仅兼容、已 deprecated。桌面/Zotero 应作为 public client，callback 仅 loopback 或 HTTPS、绝不内嵌 client secret；token 与 registration state 只能放受宿主保护的安全存储，不能放工具配置、URL、日志或模型上下文。这个 callback/secure-storage UI 与 rotation/revocation 恢复面是独立产品工作，MVP 不广告 OAuth；需要时应以单独的 host OAuth adapter 做 explicit consent、origin/issuer binding 和 fail-closed storage failure。[MCP authorization](https://modelcontextprotocol.io/specification/draft/basic/authorization)、[2026 authorization changes](https://blog.modelcontextprotocol.io/posts/2026-07-28/)、[OAuth 2.1 client guidance in 2025 spec](https://modelcontextprotocol.io/specification/2025-03-26/basic/authorization)

## C10/Q20 OAuth-protected MCP revalidation (2026-09-04)

**结论：OAuth 已足够影响正式 remote MCP 的可用性，但不应塞进当前 MCP Tool Source MVP；Q20 应作为单独 change 实现。** 这不是“目录里有多少 OAuth server”的生态占比主张，而是有边界的四个主流正式托管端样本：一个明确 OAuth-only，三个都把 OAuth 作为 interactive path，后面三个另有 token 替代。故一个只会 HTTP JSON-RPC、却没有 OAuth 的 client 仍会实质性地无法接入 Notion；同时也不应把所有 remote MCP 错说成 OAuth-only。MCP 自身将 HTTP authorization 定为 OPTIONAL，却规定支持时 HTTP 实现 SHOULD 遵循该授权规范；stdio 则 SHOULD NOT 使用此流程，而从环境取得 credential。这一差别不把 Zotero 变成 stdio client：启动/监管本地子进程仍在现有 runtime 范围外。[MCP authorization scope](https://modelcontextprotocol.io/specification/draft/basic/authorization)

| 正式托管服务（本次有界样本） | remote transport 实证 | 鉴权结论 | 对 Q20 的含义 |
| --- | --- | --- | --- |
| Notion `https://mcp.notion.com/mcp` | 推荐 Streamable HTTP，legacy SSE 仅 fallback；其 stdio 配置实际是 `mcp-remote` 本地桥。 | **OAuth required**：官方 FAQ 明言当前没有 non-interactive authorization；另一个 bearer-token OSS server 已不积极维护，不能当 hosted endpoint 的能力。 | 没有 OAuth 就不能连接该正式 hosted server。[Notion connection/FAQ](https://developers.notion.com/guides/mcp/get-started-with-mcp) |
| GitHub `https://api.githubcopilot.com/mcp/` | 正式 remote `type: http`（GitHub 文档将 HTTP 定义为 Streamable HTTP）。 | **OAuth default，PAT alternative**；PAT 可被 Enterprise Managed User 或组织策略禁用。 | 有安全存储的 PAT adapter 可覆盖一部分账户，不能保证覆盖 OAuth-only policy 环境。[GitHub remote OAuth/PAT](https://docs.github.com/en/copilot/how-tos/provide-context/use-mcp-in-your-ide/set-up-the-github-mcp-server) |

| Cloudflare API MCP `https://mcp.cloudflare.com/mcp` | Streamable HTTP；历史 `/sse` 是同一 handler alias，非 deprecated HTTP+SSE transport。 | **OAuth recommended，API token alternative**（user/account token 可作 bearer）。 | 显式配置、受保护存储的 API token 可作为窄 MVP path；不等于无 OAuth 完整支持。[Cloudflare server/auth](https://developers.cloudflare.com/agents/model-context-protocol/cloudflare/servers-for-cloudflare/) |

这四个服务都不是 “local stdio 无 OAuth” 的反例：Notion 的 `mcp-remote` 或 GitHub 的本地 server 只是本机进程与远端/凭据之间的桥接；它们不改变 hosted service 的授权政策。样本也没有覆盖全部供应商，不能据此量化“多数”。但它足以给产品边界做判断：remote OAuth 不是罕见的边缘情形，且已出现 OAuth-only 的正式工具源。

完整 desktop OAuth 是独立安全/UX 子系统，而非给现有 Streamable HTTP 请求补一个 `Authorization` header。Zotero client 至少要：在 401 `WWW-Authenticate: resource_metadata` 或规范 well-known 路径执行 RFC 9728 protected-resource discovery；同时支持 RFC 8414 与 OIDC discovery；以最小 scope 注册/取得 client ID（Client ID Metadata Document 优先、DCR 仅兼容）；为**每一次**授权生成和持久化绑定的 `state`、PKCE verifier、原始 server/resource 与已验证 issuer；把 RFC 8707 `resource` 同时放进 authorization 和 token 请求；以 loopback 或 HTTPS redirect 打开外部浏览器、接收 callback、自己验证 `state`，并在将 code 送 token endpoint 前验证 RFC 9207 `iss`。规范要求 client 使用 Protected Resource Metadata、两种 AS discovery 和 resource indicator；access token 只能放每个 HTTP request 的 Bearer header、不得进入 URL。[MCP authorization requirements](https://modelcontextprotocol.io/specification/draft/basic/authorization)

随后还要按 `(configured MCP origin, canonical resource, issuer, account/session)` 隔离 client registration、access token 与可能轮换的 refresh token；安全存储不可用时 fail closed，绝不写配置、日志、tool args 或模型上下文。401 要有限次 refresh/重新授权并保留原 request；403 `insufficient_scope` 要经用户确认作有上限的 scope-union step-up，而不是静默扩大权限；用户取消、callback 超时、issuer/resource/state mismatch、refresh rotation 失败与 revoke/invalid grant 都必须清除相应状态并给出可重新连接的非敏感错误。refresh token 并非保证会发放，且规范要求其在传输和存储中保密。[refresh-token rules and scope challenge](https://modelcontextprotocol.io/specification/draft/basic/authorization)

`@modelcontextprotocol/client@2.0.0` 已能代做相当一段**协议**工作：`StreamableHTTPClientTransport` 接受 `OAuthClientProvider`，在无 token 时 discovery、registration/lookup 和 browser redirect，`finishAuth()` 可完成 code exchange、RFC 9207 `iss` 验证并保存 token；transport 在 401 后可触发一次 provider 更新后重试，也提供受限的 insufficient-scope reauthorization。它会以 RFC 8707 resource 绑定请求。可是它有意把最关键的宿主责任留给 `OAuthClientProvider`：注册/令牌/PKCE verifier/discovery state 的持久化、redirect 的打开与 callback 接收；示例明确要求宿主比对 CSRF `state`，SDK **不**验证它，并要求生产使用 OS keychain/secure storage。SDK 的 `node >=20` 发布声明和前述 Zotero bundle 风险也仍成立，因此即使用 SDK 也不能省掉 Q20 的 host bridge、secret-storage 与 UI 工作。[SDK OAuth contract](https://ts.sdk.modelcontextprotocol.io/v2/clients/oauth.html)、[immutable client 2.0.0 manifest](https://registry.npmjs.org/@modelcontextprotocol/client/2.0.0)

**Q20 建议：单独 change 做，不阻塞当前 MVP。** 当前 MVP 只接受 HTTPS remote Tool Source 的无认证或产品明确支持、用户显式配置且安全保存的 static bearer/API token；收到 401 OAuth challenge 时返回稳定 `oauth_not_supported`（不自动打开 URL、不降级到 token、不泄露 challenge body）。这使当前承诺可诚实表述为“remote non-OAuth Tool Source”，不是“完整 MCP Tool Source”。后续 Q20 change 的完成条件应包含：Zotero 7/9 callback 可行性与 secure-storage 适配的设计/实测、OAuth lifecycle/rotation/reconnect/error-recovery、per-origin issuer/resource binding、explicit consent and disconnect UI、审计/redaction、以及至少一个 OAuth-only hosted server（Notion）和一个 token-alternative server 的端到端验证。届时也应复审 v2 browser-condition bundle；若仍不可接受，就在同一 host OAuth adapter 中自行实现所需 OAuth subset，而非为了 OAuth 重新引入 Node-only transport。

# 自动化策略

## 授权矩阵

| 动作 | Cron | 交互式常驻请求 | 所需证据 |
| --- | --- | --- | --- |
| 刷新本地索引/目录 | 允许 | 允许 | 回执及刷新/变更计数 |
| 搜索本地投影 | 当任务声明时允许 | 允许 | 缓存新鲜度加外部主张的实时确认 |
| 读取实时文献库/Synthesis 状态 | 以一次有界扫描允许 | 允许 | 返回的引用与新鲜度事实 |
| 监控已注册运行或同步通知 | 以一次有界扫描允许 | 允许 | 运行/事件 ID 与回执 |
| 产出整洁度、工作流状态或关注项提案 | 允许 | 允许 | 候选原因与下一步实时检查 |
| 校验 Zotero 托管工作流 | 未随附于 cron | 通过通用/CLI 允许 | 当前选择、工作流/选项校验、提供方兼容性 |
| 提交工作流 | 绝不允许 | 仅针对已审阅的当前范围允许 | 当前操作员指令、有界并发、Zotero 审批路径 |
| 执行自有智能体交接 | 绝不允许 | 委托给通用 | 交接契约、本地校验、应用回执 |
| 修改 Zotero 或应用智能体输出 | 绝不允许 | 使用通用/CLI 契约 | 当前请求、精确目标/效果、Zotero 侧审批 |
| 破坏性维护 | 绝不允许 | 需要当前目标级别的人工决策 | 诊断、提案、审批、事后状态 |

本地缓存与日志写入属于常驻簿记，并非变更 Zotero 的授权。先前的审批、已观察到的原生提交、待处理工作流、缓存候选或定时提案均不得被提升为新的写入。

## 工作流模式与委派

从实时描述中选择工作流所有权。Zotero 托管执行使用通用任务策略与精确的 CLI 汇合点；Zotero 插件的原生队列拥有待处理单元排序、有界接纳与槽位生命周期。已接纳的运行可以被注册并监控。提供方配置决策、工作流选项、来源分组判断与有限的研究解读归继承自通用的任务 Skill 负责。

当工作流声明自有智能体执行时，将整个交接委托给通用：准备/检视请求、执行语义工作、校验每个结果、应用映射并检视持久的应用回执。常驻关注的运行与通知不监督 `agentRunId`。

即使存在缓存的目录条目，也要使用实时工作流发现。缓存的定义有助于选择，但不能确立当前的执行模式、后端兼容性、权限或结果模式。

## 原生提交与队列监督

通过随附的 CLI 描述并校验当前请求：

```sh
zotero-bridge workflow describe --workflow <workflow-id>
zotero-bridge workflow validate \
  --workflow <workflow-id> --selection '<reviewed-selection>' \
  --workflow-options '<reviewed-options>'
```

检视精确的选择引用、独立的 `inputs` 与 `validateSelection` 契约、工作流 ID、必需选项、提供方要求、候选生成规则、不可变单元分组、期望输出与审批边界。空、过期或非预期的选择都是未解决的调用范围：操作员修正后的引用构成一次新的已审阅调用，而原始的校验失败仍关联其原始引用。切勿在本地重建已准备的单元，也切勿把缓存的目录数据当作实时校验。

在操作员授权该精确的已审阅范围与有界并发后，提交一次：

```sh
zotero-bridge workflow submit \
  --workflow <workflow-id> \
  --selection '<reviewed-selection>' \
  --workflow-options '<reviewed-options>' \
  --max-concurrency <bounded-count>
```

合法的参数记录了当前已审阅范围，但不能替代 Zotero 侧的审批。宿主在接纳工作前会重新校验实时工作流契约与选择。读取返回的 `admission` 分支：直接接纳时保留 `workflowRunId`；宿主队列接纳时保留 `submissionId`、计数、队列链接以及不可变单元投影。当初始响应刻意表示待处理工作时，切勿凭空捏造运行句柄。

对于已排队工作，使用 `workflow submission get <submissionId>` 作为聚合接纳记录。使用 `workflow queue list` 观察活跃单元，`workflow queue cancel <queueId>` 仅用于仍处于待处理状态的单元。单元一旦被接纳，便通过 `run list --submission <submissionId>` 与之关联，并监督其真实运行。后续提交需要新的当前指令；切勿把原始授权视作无限期授予，也切勿重放接纳效果不确定的单元。

## 提供方配置与并发

工作流选择与选项并不编码后端提供方配置。如果工作流要求后端拥有的提供方选项，请使用通用列出/描述后端配置，独立于工作流输入校验提供方 JSON，并通过精确的 CLI 契约提交，使二者结合。连接配置与提供方配置是相互独立的概念。

交互式提交默认并发为 1。较高的 `--max-concurrency` 至多接纳指定数量的原生单元并发执行，且必须在考虑后端/提供方限制、成本、条目独立性、回写时长与监控能力后显式批准。该绑定仅属于本次已接受的提交；它不授权未来的工作。

分别记录返回的 `submissionId`、每个单元的 `queueId` 以及每个已接纳的任务或 `workflowRunId`。待处理单元已是已接受原生提交的一部分；它们不需要常驻重新启动，也不应被解读为失败。若接纳不确定，请在另一次调用前检视原始提交与按提交过滤的任务列表。

## Cron 与维护

每个随附 cron 都是 Zotero 只读且一次扫描。它可以更新 `state.sqlite`、产出关注项，并在无可汇报差异时输出 `[SILENT]`。它不能等待、请求审批、提交、应用、在未经核实的情况下确认事件、调用用户选择的脚本或写入任意路径。

工作流状态分诊识别需要审阅的被关注运行。文献库整洁度目前识别重复标题的候选。Synthesis 关注项汇报实时排序条目。这些都是诊断与提案。在修复前，调用合适的通用任务，重新读取当前对象，说明效果，并取得当前授权。

Synthesis 缓存、索引、sidecar、图谱或指标的维护遵循通用 Synthesis 与 CLI 契约。空队列或过期的本地投影并不是修改派生状态的充分理由。

## 交互与汇报

对于等待中的运行，请在回复或连接前检视其实时 `skillRunId` 与已声明动作。CLI 中的权限 ID 仅作观察之用；审批仍位于带作用域的 Zotero UI 中。通知事件仅在其请求或暗示的后续动作已被实际处理后才可确认。

汇报关注项时请附带其原因、条目/运行/事件标识、相关时附缓存新鲜度以及下一步安全的实时检查。区分提案与已启动运行、已启动运行与终态结果，以及终态结果与已核实的产物、制品或 Zotero 变更。失败回执保留稳定的错误码，并说明重试前所需的实时重读。

## 自然语言自动化决策

常驻请求常使用操作性语言而不指明实际的授权边界。请使用以下决策模式。

### "监控这个工作流"

判断：

- 用户是否提供了 `workflowRunId`，是否需要注册已知运行；
- 用户是想要一次当前状态检查，还是指既有的循环时刻表；
- 哪些状态或事件需要汇报；
- 是否允许交互，或本次扫描只能汇报；
- 预期输出是否需要超出运行状态的产物/制品核实。

策略：

- 仅注册真实的 Zotero 托管工作流运行；
- 执行一次 `run watch` 扫描；
- 使用实时运行命令进行交互；
- 不要在完成前等待、休眠或轮询；
- 不要把自有 `agentRunId` 放入被关注的运行；
- 不要仅仅因为运行到达终态就确认通知。

### "在我需要关注时告诉我"

判断：

- 哪些域属于此范围：失败/停滞的运行、未处理事件、重复候选、Synthesis 关注项，还是全部；
- 用户是想要每个候选还是仅满足阈值者；
- 这是当前报告还是既有的循环时刻表。

策略：

- 运行有界的关注项产出扫描；
- 保留每个候选的原因与标识；
- 将 `attention` 视作已完成的提案/报告；
- 切勿自动变更、重新提交、修复或确认；
- 任何后续研究或策展请使用通用任务策略。

### "保持我的文献库整洁"

该措辞永远不足以构成变更授权。请将其转化为：

1. 声明的诊断域；
2. 一次候选报告扫描；
3. 对候选对象的实时重读；
4. 通用 Curation 提案；
5. 单独当前目标级别的决策；
6. 若批准，则执行已核实的写入并保留持久回执。

定时文献库整洁度扫描目前识别重复标题候选。重复标题并非重复项的证明，也不能选择保留项。

### "每晚运行分析"

将其拆分：

- 有限的工作流选择与校验；
- 操作员批准的校验/提交范围；
- 外部时刻表配置；
- 每次运行的监控；
- 产出核实。

常驻服务无法安装或修改 cron。随附的 cron 任务刻意不会提交工作流。请将所请求的频率作为外部配置需求汇报；切勿修改 cron 文件，也切勿暗示该时刻表已存在。

### "基于我的文献库回答问题"

使用常驻索引进行发现或变更对比，然后将有限的问题委托给通用 Query。实时确认当前事实。切勿把仅基于缓存的结论呈现为当前 Zotero 状态。

### "自动修复一切失败"

拒绝该隐含的笼统授权。不同的失败可能代表：

- 无远端效果；
- 远端成功但响应丢失；
- 原生接纳不完整；
- 缺失产物或制品；
- 提供方不可用；
- 权限被拒；
- 本地投影过期；
- 破坏性策展含义不明。

对失败进行分类并返回下一步安全的检查。切勿把"自动"一词当作变更或重放的授权。

## 原生提交授权生命周期

### 准备

Zotero 托管请求仅在满足以下条件时才可进入授权审阅：

- 实时工作流描述可用；
- 实时描述暴露独立的执行输入与候选生成契约；
- 原始当前选择在无常驻候选或分组推断的情况下被解析；
- 完整选择通过实时工作流校验；
- 必需的工作流选项已被明确并通过校验；
- 提供方要求已被识别并通过独立配置契约校验；
- 受支持的执行模式是 Zotero 托管；
- 期望的产物、制品、实时变更与交互点已知；
- 拟议的并发是本次请求的有限正数上限。

审阅记录需保持以下各项相互独立：

- 工作流身份与结果；
- 精确选定的引用或声明的无选择形式；
- 工作流选项；
- 提供方配置身份与已校验的提供方 JSON；
- 候选选择与不可变分组行为；
- 拟议的原生接纳上限；
- 期望的单元到来源关联；
- 期望的运行与产出证据。

### 审阅

操作员审阅：

- 工作流结果；
- 精确选定的引用；
- 执行成员与分组契约；
- 候选选择与校验契约；
- 期望的原生单元数量或形态；
- 期望的提供方/执行边界；
- 工作流选项及其范围效果；
- 本次已接受提交的并发；
- 期望的运行/结果证据；
- Zotero 侧审批时序。

审阅并不创建队列条目或持久授权。任何期望的变更都需要针对当前实时上下文重新校验。

### 授权

授权是当前的且针对本次调用：

- 用户指令必须指已审阅的工作流、选择、选项与提供方范围；
- 当有界并发大于 1 时，它必须是已审阅效果的一部分；
- 先前的提交并不授权另一次提交；
- 已接受原生提交内的待处理单元不需要新的常驻启动决策；
- 提高并发需要在调用前进行显式考虑与授权；
- Zotero 侧审批保持独立。

切勿在常驻状态中持久化"已批准"标记。那会把过去的决策转化为可复用的授权。

### 再次校验

在远端提交之前：

- 重新描述工作流；
- 确认执行模式；
- 解析当前选择；
- 校验完整选择与工作流选项；
- 重新校验独立选定的提供方配置；
- 保留精确的 JSON 绑定，不要把提供方字段移入工作流选项；
- 确认期望的单元分组与产出契约；
- 确认已授权的并发上限。

任何不匹配在远端效果产生前失败关闭。

### 通过 Zotero 接纳

提交已审阅请求一次。然后：

1. 在选择监控路径前读取 `admission`；
2. 直接接纳时，保留返回的任务标识与 `workflowRunId`；
3. 宿主队列接纳时，保留 `submissionId`、单元计数、队列链接以及每个不可变 `queueId`；
4. 检视提交的投影中的待处理、已接纳、终态、失败与已取消单元；
5. 通过提交谱系过滤器关联已接纳任务；
6. 仅在目标单元仍处待处理时使用队列取消；
7. 仅在真实运行句柄出现后使用运行取消或交互；
8. 在整个监督过程中将源引用与期望输出附着到每个单元。

Zotero 插件拥有待处理单元排序、接纳与槽位释放。常驻配置不预留单元、不启动下一条目，也不运行重放工作器。

### 监督与汇报

交互式提交证据说明：

- 直接或宿主队列接纳；
- 已排队时的 `submissionId`；
- 聚合的单元计数与链接；
- 不可变单元标识；
- 已接纳的任务与运行标识（若已存在）；
- 已请求的待处理取消回执；
- 不确定的传输或状态证据（若已存在）。

监督报告区分：

- 已被原生队列接受的待处理单元；
- 在接纳前被取消的单元；
- 已接纳或运行中的任务；
- 终态成功的任务；
- 终态失败的任务；
- 其产物、制品或实时变更验证不完整的任务。

此证据证明已观察到的原生接纳与执行状态。它并不能证明产出质量、产物交付、Zotero 回写或用户研究结果的完成。

## 提供方、选项与不支持的提交

交互式路径将一份已审阅请求发送给宿主校验，并把候选生成与不可变分组委托给实时工作流契约。出现以下情况时请路由到通用：

- 必需的工作流选项需要语义选择或澄清；
- 需要选择或校验提供方配置；
- 工作流使用自有智能体执行；
- 需要无选择执行；
- 任务需要自定义结果处理或回写。

切勿剥离必需选项、悄无声息地选择默认提供方、把自有工作流转化为 Zotero 托管工作流，或在本地重建宿主的已准备单元。

## 并发决策

默认并发 1 是安全边界，而非性能事故。所选的值将成为本次提交在原生队列中的接纳上限。

仅在以下条件下提高并发：

- 条目相互独立；
- 提供方/后端容量已知；
- 预期成本可接受；
- 监控可区分每个运行；
- 提交谱系可将每个已接纳单元与其来源标识相关联；
- 单个失败不会使其他条目失效；
- 操作员授权本次提交的确切上限。

在以下情况下不要提高并发：

- 选择存在重叠；
- 写入可能冲突；
- 提供方配额不确定；
- 可能需要运行交互；
- 回写可能在材质差异显著的时长内持有原生槽位；
- 工作流结果顺序重要；
- 较早的提交状态未知。

并发值仅适用于当前提交调用。它配置 Zotero 的原生队列；它不创建常驻队列工作器、不预留本地条目，也不授权未来的提交。待处理的原生单元已是已接受的工作，不得被重新提交以模拟进度。

## Cron 决策模型

随附 cron 拥有节奏；服务拥有单次扫描。保持职责分离。

Cron 可以：

- 刷新本地投影；
- 对比状态；
- 监控已知运行一次；
- 同步轻量通知；
- 产出工作流状态、整洁度或关注项报告；
- 输出 `[SILENT]` 表示 `unchanged`。

Cron 不得：

- 提交或重新提交工作流；
- 执行自有交接；
- 在动作未处理前确认事件；
- 变更 Zotero；
- 应用结果；
- 运行破坏性维护；
- 等待交互；
- 创建新的时刻表。

如果用户请求新的频率，请汇报：

- 期望的服务命令；
- 读/写权限；
- 期望的汇报阈值；
- 外部调度需求。

切勿在常规 Skill 执行过程中编辑配置时刻表。

## 关注项与升级剧本

### 等待中的运行

1. 读取实时运行状态；
2. 解析当前 `skillRunId`；
3. 检视已声明动作；
4. 汇报所需的交互；
5. 仅在匹配的通用/CLI 契约下回复或连接；
6. 在处理后确认相关通知。

### 失败的运行

1. 保留运行与工作流 ID；
2. 检视结构化失败与期望输出；
3. 判断是否存在产物/制品；
4. 区分提供方失败、工作流失败、缺失输出与 Zotero 应用失败；
5. 把有限的语义重试决策路由到通用；
6. 切勿从通知处重新提交。

### 不确定的提交

1. 保留已返回或先前观察到的 `submissionId`、单元 `queueId`、选择引用与结构化错误；
2. 在寻找替代操作前检视原生提交投影；
3. 通过按提交过滤的任务发现关联已接纳工作，并核实真实运行状态；
4. 在调和已接纳运行与被关注状态时，不要把被关注的运行日志当作队列权威；
5. 切勿重放选择或接纳效果未知的任何单元；
6. 仅在证明较早调用未创建已接受提交或已接纳任务并取得新授权后，才进行新提交。

### 整洁度候选

1. 保留候选原因与条目引用；
2. 读取两个实时对象；
3. 判断它们是重复、版本还是误报；
4. 把提案构建委托给 Curation；
5. 要求精确的破坏性授权。

### Synthesis 关注项

1. 检视实时关注项条目；
2. 解析模型身份与新鲜度；
3. 把解读委托给通用 Synthesis；
4. 单独诊断维护动作；
5. 切勿仅凭队列成员资格变更派生状态。

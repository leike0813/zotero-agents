## Why

MinerU precision extraction rejects PDFs above its per-file page limit, while the current workflow submits every PDF as one task and can only materialize one returned bundle. Long books, theses, and reports therefore fail even when the API can process page ranges from the same source file.

## What Changes

- Add a MinerU preflight split path for PDFs with more than 200 pages.
- Submit long PDFs as ordered page-range tasks using the existing `generic-http.steps.v1` provider and preflight aggregate protocol.
- Merge all successful MinerU bundles into the same final Markdown and image layout used by short PDFs.
- Prefer chapter/section-aware split boundaries from PDF outline/bookmarks when available, with balanced page ranges as the fallback.
- Preserve the current workflow protocol and Generic HTTP provider contract.

## Capabilities

### New Capabilities

- `mineru-long-pdf-page-range-splitting`: Long PDF page-range planning, request fan-out, and aggregate apply behavior for the MinerU workflow.

### Modified Capabilities

- `mineru-workflow-http-pipeline`: MinerU requests may be generated by a buildRequest hook when preflight page-range context is present.
- `mineru-workflow-result-materialization`: MinerU materialization may merge multiple ordered bundles into the same final output shape.

## Impact

- Affected code: `workflows_builtin/mineru`, builtin workflow manifest, and MinerU workflow tests.
- No provider API changes, no workflow protocol changes, and no new runtime dependency.
- The implementation still uploads the original PDF for each page-range task; files above MinerU's upload-size limit remain out of scope.

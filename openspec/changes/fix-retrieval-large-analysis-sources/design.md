# Design

## Context

Host 通过受管笔记解析器确认 canonical analysis，序列化其逻辑 payload，并用现有逻辑哈希作为 `sourceVersion`。目前 Host 和跨语言校验都把 262,144 个 UTF-16 单元当作分析来源总长上限。Rust 检索已经支持长 Markdown 连续分段，并具备绝对范围预览和重建前后目录校验。

## Goals / Non-Goals

复用 Host 的受管笔记资格判定和检索的私有证据路径。保留当前存储格式、索引分块规则和公共词法检索契约。

## Decisions

1. **来源预算与响应预算独立。** 保留受管 payload 解码的字节上限，并给规范化分析文本设 1,048,576 个 UTF-16 单元上限，覆盖本次观察到的最大来源。超过 262,144 单元的分析由 `scanMode: "retrieval"` 枚举，读取时须指定范围，每页至多 65,536 单元。Host、私有契约和 Rust 按来源类型一致地校验总长、请求范围及响应。提高整段响应限额会扩大跨边界传输，仍把来源资格和单次传输混在一起。
2. **复用一套完整分段校验。** 扩展 Rust 的现有 Markdown 分段读取，按来源使用相应位置语义。分析使用 `analysis_field` 和根字段 `$`，以 canonical JSON 文本中的绝对 UTF-16 坐标为基准。Host 对同一逻辑版本返回连续范围。只有为保护代理对才允许收短页尾，下一页从实际页尾继续。来源读全后沿用现有切分与编码策略。
3. **回查和发布沿用现有边界。** 语义搜索和索引预览按存储的片段范围重读并校验，避免为一个结果重传完整分析。重建继续复核完整目录后再发布。逻辑版本、note 引用和坐标沿用现有定义，旧索引无需迁移。支持长分析的完整索引由显式重建生成。

## Risks / Trade-offs

- 每页重读和规范化同一受管笔记有成本。先用合成大样本和真实库记录分段次数、耗时及现有截止时间内的结果。若需要复用规范化文本，须让复用受活动操作和可验证的来源版本约束，避免遮蔽页间修改和最终目录复核。
- 源错误可能直到目录后续页才出现。合成测试单独验证已知大小的分析来源，真实库验收全程保留原来的四类选择和有限错误诊断。

## Migration Plan

成套构建 Host 和 sidecar。用现有发布指针验证重建前后的状态，全量重建完成后原子发布。回退时使用旧 Host 与旧 sidecar 配套版本，并按现有索引兼容规则恢复。

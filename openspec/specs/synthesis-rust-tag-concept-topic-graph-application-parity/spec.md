# synthesis-rust-tag-concept-topic-graph-application-parity Specification

## Purpose

Define typed Rust ownership and differential parity for Tag, Concept, and Topic Graph applications.

## Requirements

### Requirement: Three knowledge domains SHALL execute through typed Rust applications
The private candidate SHALL expose distinct typed Tag Vocabulary, Concept KB, and Topic Graph application owners whose policy is implemented above explicit repository and compute ports without generic command dispatch.

#### Scenario: Candidate application inventory is audited
- **WHEN** the Rust candidate source and package are inspected
- **THEN** each domain has a typed module and repository boundary
- **AND** no string-selected application state machine, Node fallback, or production capability is present

### Requirement: Differential evidence SHALL use independent owners
The parity harness SHALL run the frozen Node oracle and Rust candidate with physically distinct mutable repository and canonical roots while sharing only a read-only versioned fixture.

#### Scenario: A corpus case executes
- **WHEN** either implementation mutates its isolated state
- **THEN** the other implementation cannot observe that state except through the final comparison report

### Requirement: Reports SHALL cover complete stable observations
The checker SHALL compare public DTOs, stable codes and diagnostics, table-specific projections from all 51 tables, cache and operation rows, and close/reopen observations.

#### Scenario: A durable side effect differs
- **WHEN** one implementation produces a different stable row, receipt, or reopened state
- **THEN** the checker fails with the domain, case, and observation path

### Requirement: Unowned surfaces SHALL remain unchanged
The cluster SHALL NOT write Topic canonical assets, canonical journal or receipt state, invoke downstream applications, or contact a production Host.

#### Scenario: All three aggregates coexist
- **WHEN** one fixture seeds Tag, Concept, and Topic Graph facts
- **THEN** the canonical tree and downstream application rows remain unchanged
- **AND** no Checkpoint, Bundle, WebDAV, Debug, or automatic rebuild action occurs

### Requirement: Candidate targets SHALL run the cluster gate
Every supported Rust candidate workflow target SHALL run the versioned checker before candidate smoke and remain within existing package-size budgets.

#### Scenario: A target omits parity
- **WHEN** workflow inventory does not execute the new checker before smoke
- **THEN** the candidate contract test fails
